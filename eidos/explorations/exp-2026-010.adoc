== Core Hypothesis
Executing a controlled, worktree-isolated 2-arm head-to-head benchmark in **Antigravity** (**Eidos-Bench**) across $N = 20$ curated software engineering tasks (5 tasks across each of 4 architectural archetypes, plus a 5-step sequential evolution chain $T_1 \to T_5$) using the latest Eidos engine (`v0.21.0+`) will demonstrate that an **Eidos-Powered Antigravity Agent (`Arm B`: Living Specs + Discovery CLI + `eidos drift` Gate)** significantly outperforms a **Standard Antigravity Agent (`Arm A`: Code + Tests + standard handwritten `AGENTS.md`, without Eidos)** across four measurable dimensions:

1. **Localization & Token Efficiency (`Discovery Lift`)**: Reducing pre-edit exploratory input token consumption by **`>= 45%`** and exploratory search/read tool calls (`grep`, `find`, `read_file`) prior to the first file edit by **`>= 40%`** via `eidos index repo-map`, `eidos context`, `eidos index find-symbol`, and `eidos index blast-radius`.
2. **Architectural & Policy Survival Rate (`Guardrail Lift`)**: Reducing silent architectural regressions—solutions that pass local functional unit tests while violating a system policy (`POL-*`), re-introducing a rejected design alternative (`DEC-*`), leaking undocumented public surface symbols (`== Public Surface`), or breaking interface contract parity (`CTR-*`)—by **`>= 85%`**.
3. **Autonomous Self-Healing Rescue Rate (`Drift Gate Lift`, measured within `Arm B` trajectories)**: Converting **`>= 80%`** of first-draft contract, invariant (`INV-*`), or spec-coverage omissions into clean, self-remediated completions prior to turn termination via `eidos drift --uncommitted` and `eidos validate`.
4. **Longitudinal Anti-Rot Resilience (`Arm B` vs. `Arm A` over $T_1 \to T_5$)**: Preserving **`>= 90%`** task resolution and zero stale-symbol hallucinations at step $T_5$ of a sequential multi-PR refactor chain, whereas `Arm A` (`Standard AGENTS.md`) degrades by **`>= 30%`** as static markdown instructions drift from source code across $T_1\text{–}T_4$.

== Questions & Spikes
* **Questions to Answer**:
  1. *Head-to-Head Outcome Lift in Antigravity (`Arm B` vs. `Arm A`)*: When two identical Antigravity subagents (`define_subagent` + `invoke_subagent`) are given the exact same engineering prompt on isolated orphan Git worktrees, how much does Eidos improve composite pass rate (`Pass@1_Func` + `Pass@1_Arch`), blast-radius recall, and token efficiency over a realistic handwritten `AGENTS.md`?
  2. *In-Trajectory Attribution (Discovery vs. Drift Gate without Extra Arms)*: By inspecting `Arm B`'s `.jsonl` conversation transcripts at two checkpoints—**Checkpoint 1 (Pre-First-Gate Edit)** vs. **Checkpoint 2 (Post-`eidos drift` Final State)**—what fraction of `Arm B`'s architectural advantage is already achieved upfront by `eidos context`/`index` discovery versus rescued post-edit by `eidos drift`?
  3. *Deterministic, Zero-LLM Grading Oracle*: How can we grade functional correctness, hidden constraint adherence (`DEC-*`, `POL-*`), blast-radius completeness, and contract parity 100% deterministically (without noisy LLM-as-a-judge scoring) across both `Arm A` (where `eidos/` is stripped) and `Arm B`?
  4. *Subagent & Git-History Isolation in Antigravity*: How should we configure `define_subagent` system prompts and orphan Git worktrees (`git checkout --orphan`) so that (a) `Arm A` subagents do not inherit the parent workspace's Eidos `<RULE>` or `eidos` CLI, and (b) neither arm can inspect historical commits via `git log` / `git blame`?
* **Spikes**:
  - `spike-antigravity-worktree-harness`: Build an automated benchmark provisioner that creates paired **orphan Git worktrees** (`arm_a_baseline` with `eidos/` and dogfood-spec tests stripped plus a standard ~50-line developer `AGENTS.md`; `arm_b_eidos` with full `eidos/`, `.agents/plugins/eidos/skills/`, and `eidos` `v0.21.0` CLI) and defines the paired Antigravity subagent runners (`bench-arm-a-baseline` vs. `bench-arm-b-eidos`).
  - `spike-20-task-suite-and-hidden-oracle`: Curate 20 self-contained benchmark tasks across 4 archetypes (plus a 5-task sequential chain $T_1 \to T_5$) and implement the **Deterministic Grading Oracle** (`pytest` behavioral suite + AST architectural/decision boundary suite + post-hoc `eidos validate`/`eidos drift` overlay check).
  - `spike-ab-subagent-execution-and-telemetry`: Execute the head-to-head benchmark across Antigravity subagent sessions, parsing `.system_generated/logs/transcript.jsonl` to measure pre-edit tokens, tool-call trajectories, first-pass blast-radius recall, `eidos drift` self-healing rescues, and architectural survival rates.
* **Exit Criteria**: Max duration `5_days`; automated, reproducible 2-arm Antigravity benchmark harness capable of provisioning orphan worktrees, grading any subagent worktree deterministically in `< 5s` with zero LLM judge calls, and producing empirical head-to-head results across all 4 usefulness pillars.

== Findings & Learnings
Empirical execution of all three spikes (`spike-antigravity-worktree-harness`, `spike-20-task-suite-and-hidden-oracle`, and `spike-ab-subagent-execution-and-telemetry`) in **Antigravity** against **Eidos `v0.21.0`** (`N = 20` deterministic discovery tasks + `12` live head-to-head subagent sessions across `bench-arm-a-baseline` and `bench-arm-b-eidos` on history-stripped orphan Git worktrees) established five quantitative findings on end-to-end Eidos usefulness:

1. **Deterministic Discovery & Token Compression (`Spike 2`, $N = 20$ tasks across 4 archetypes)**:
   * `eidos context` + `eidos index` achieved **`100.0%` (`20/20`) owning spec localization recall**, **`100.0%` (`20/20`) target source file recall**, and **`100.0%` (`20/20`) governing guardrail (`DEC-*`, `INV-*`, `POL-*`, `CTR-*`) recall**.
   * Mean `guardrails` context slice size was **`608.7` tokens** versus **`43,253.7` mean raw package tokens** (`290,553` total `src/eidos/` tokens), delivering a **`98.6%` token reduction** compared to scanning raw package files.
2. **Composite Outcome Lift & Blast-Radius Protection (`Spike 3`, 12 Live Subagent Runs)**:
   * **`Arm B` (`bench-arm-b-eidos`) achieved `100.0%` (`6/6`) composite functional + architectural pass rate (`Pass@1_Composite`) and `100.0%` (`6/6`) zero-drift completion (`Drift_Clean`)**, compared to **`66.7%` (`4/6`) `Pass@1_Composite` and `0.0%` (`0/6`) spec/surface parity in `Arm A` (`bench-arm-a-baseline`)**.
   * In `T2_1_CONTEXT_CLI_CONTRACT_PARITY` (adding `--include-decisions / --no-include-decisions`), `Arm A` (`8749290e`) passed its local unit test (`tests/test_context.py`) but **broke the repository's CLI contract snapshot (`tests/fixtures/cli_command_tree.json`)**, whereas `Arm B` (`94894e7d`) updated all 3 code components (`context_command.py`, `context.py`, `graph_index.py`), `cli_command_tree.json`, and 4 governing `.adoc` specs (`CTR-EIDOS-CLI`, `CMP-CLI-CONTEXT-COMMAND`, `CMP-TIERED-CONTEXT-COMPRESSOR`, `CMP-GRAPH-STORAGE`).
3. **In-Trajectory `eidos drift` Self-Healing Rescue (`Checkpoint 1 -> Checkpoint 2`)**:
   * In **`2/6` (`33.3%`)** of `Arm B` runs (`T2_1` and `T4_1`), the subagent's initial code edit (`Checkpoint 1`) left structural drift (`3` un-synced component specs in `T2_1`; `1` undocumented public surface function in `T4_1`).
   * Running `eidos drift --uncommitted --json` caught **`100%` (`2/2`)** of these omissions with exact `remediation_suggestions`, and the agent autonomously fixed every finding before turn termination (`Checkpoint 2`, `is_clean: true`).
4. **Pre-Edit Discovery Speedup on Non-Obvious Architectural Decisions (`T1_4` `DEC-AUDIT-INDEX-SCOPED-DISCOVERY`)**:
   * When an architectural constraint is recorded in a living spec (`DEC-AUDIT-INDEX-SCOPED-DISCOVERY` in `delta-auditor.adoc`) rather than inline code comments (`src/eidos/core/lifecycle/audit.py`), `Arm B` (`85d84c14`) ran `eidos context -f src/eidos/core/lifecycle/audit.py --tier deep --json` on Turn 2 and surfaced the exact rejected alternative (`git ls-files` subprocess discovery) in **`11` pre-edit tool calls and `10,369` tokens**—**`-31.3%` fewer pre-edit tool calls** and **`-26.6%` fewer pre-edit tokens** than `Arm A` (`25a3180a`, which needed **`16` pre-edit tool calls and `14,132` tokens** across `git log`, `grep`, and `docs/concepts/*.md`).
   * Furthermore, in `T2_1` and `T4_1`, the static ~50-line `AGENTS.md` in `Arm A` referenced a pre-refactor file path (`src/eidos/cli/context.py`, renamed in `DLT-2026-052` to `src/eidos/cli/context_command.py`), causing `Arm A` subagents to waste initial tool calls on `file does not exist` errors, whereas `Arm B` queried the live AST index (`eidos index find-symbol`) with zero broken file reads.
5. **The "Co-Evolution Token Tax" Trade-Off on Simple Single-File Edits (`T1_1`, `T3_1`, `T4_1` vs. `T1_4`, `CHAIN_T2`)**:
   * On self-contained single-file tasks where the target path or inline comment is already obvious (`T1_1`, `T3_1`, `T4_1`), `Arm B` consumes **more total tool calls (`+31%` to `+66%`) and tokens** than `Arm A` because `Arm B` loads `SKILL.md`, reads and edits `.adoc` specifications, and runs `eidos validate` + `eidos drift`.
   * However, on multi-file refactors (`CHAIN_T2`, where `Arm B` completed in **`33` total tool calls vs. `36` for `Arm A`**) and hidden-decision tasks (`T1_4`, **`25` vs. `26` total calls and `-26.6%` pre-edit tokens**), `Arm B` is both **faster and more complete**, proving that Eidos's specification co-evolution overhead is an upfront investment that pays off on cross-cutting, contract-governed, and multi-PR tasks.

== 1. Problem Statement & Motivation

Prior Eidos explorations rigorously benchmarked individual **engine subsystems and agent compliance mechanics**:
* **`EXP-2026-002` (SQLite + AST Graph Index)**: Proved `~1.2 ms` context slice latency and `97.9%` token compression vs. loading raw catalog files.
* **`EXP-2026-006` & `EXP-2026-009` (Lexical & Hybrid RRF Retrieval)**: Proved `94.4%` (`DEV`), `92.9%` (`HOLD`), and `81.2%` (`HOLD_V2`) context slice recall in sub-4ms lexical / sub-80ms warm ONNX forward passes.
* **`EXP-2026-007` (Agent Tool-Call Compliance)**: Proved across $n = 95$ real Antigravity coding transcripts that the 4 consolidated skills (`eidos`, `eidos-spec`, `eidos-plan`, `eidos-ops`) + stateless `Stop` hook (`eidos hook`) achieve `100%` skill load, `87.5%` pre-edit `eidos context` invocation, and `90.5%` proactive `eidos drift` execution.

However, measuring **engine speed**, **retrieval recall**, and **CLI invocation rates** only proves that the *mechanism* works—it does not directly quantify **end-to-end usefulness**:

[quote]
____
When an Antigravity coding agent is given a real software engineering task on a non-trivial codebase, how much does Eidos actually improve **task success**, **architectural invariant survival**, **token/turn cost**, and **multi-PR maintainability** compared to a standard repository with a normal `AGENTS.md` file?
____

Standard industry benchmarks like **SWE-bench** evaluate whether an agent can make a localized bug-fix test pass on a single turn, but they are blind to the failure modes that break AI-maintained codebases in production:
1. **Silent Architectural Violations**: An agent passes the functional unit test by importing an unauthorized container, bypassing a domain boundary, or adopting a design pattern that was previously rejected for performance/security reasons (`DEC-*`).
2. **Contract & Surface Drift**: An agent adds a CLI option, modifies an API payload, or renames an exported class without updating interface contracts (`CTR-*`) or downstream consumers.
3. **Unverified Behavioral Mutations**: An agent alters critical domain logic without updating or binding an invariant test (`INV-*`), leaving future regressions unguarded.
4. **Longitudinal Documentation Rot**: Static instruction files (`AGENTS.md`, `README.md`) help on Day 1, but because nothing enforces their co-evolution with AST changes, they silently drift across sequential PRs until they actively mislead future agent sessions.

== 2. Experimental Design: 2-Arm Head-to-Head in Antigravity

Rather than multiplying runs across synthetic intermediate arms, every benchmark task $T_i$ is executed as a direct **1v1 head-to-head** in Antigravity using two isolated custom subagents (`define_subagent` with `EnableWriteTools: true`, `Model: "inherit"`) operating on separate, history-stripped orphan Git worktrees:

```
                      ┌─────────────────────────────────────────┐
                      │   Canonical Base Commit Snapshot (HEAD) │
                      │   Orphan Git Worktree (No git log leak) │
                      └────────────────────┬────────────────────┘
                                           │
                        ┌──────────────────┴──────────────────┐
                        ▼                                     ▼
        ┌───────────────────────────────┐     ┌───────────────────────────────┐
        │             ARM A             │     │             ARM B             │
        │   Baseline Antigravity Agent  │     │    Eidos Antigravity Agent    │
        │     (Standard AGENTS.md)      │     │         (Full Eidos)          │
        ├───────────────────────────────┤     ├───────────────────────────────┤
        │ • src/, tests/, README.md     │     │ • src/, tests/, eidos/        │
        │ • Realistic ~50-line human    │     │ • Eidos AGENTS.md rule block  │
        │   AGENTS.md (repo layout,     │     │ • 4 Eidos skills (.agents/)   │
        │   pytest, style conventions)  │     │ • eidos v0.21.0 CLI:          │
        │ • eidos/ & skills stripped    │     │   - Checkpoint 1: Discovery   │
        │ • Native grep / find / read   │     │     (context / index / map)   │
        │   + pytest execution          │     │   - Checkpoint 2: Gate        │
        │                               │     │     (eidos drift / validate)  │
        └───────────────┬───────────────┘     └───────────────┬───────────────┘
                        │                                     │
                        └──────────────────┬──────────────────┘
                                           ▼
                      ┌─────────────────────────────────────────┐
                      │    Deterministic Grading Oracle         │
                      │  1. Functional & Edge-Case Pytest Suite │
                      │  2. Hidden DEC-* / POL-* AST Audit      │
                      │  3. Post-Hoc Eidos Drift/Contract Check │
                      │  4. Transcript JSONL Telemetry Parser   │
                      └─────────────────────────────────────────┘
```

=== 2.1 Realistic Baseline Construction (`Arm A`)

In `Arm A`, we simulate what a well-maintained repository looks like *before* adopting Eidos:
* `eidos/` and `.agents/plugins/eidos/` are removed from the worktree, and `PATH` excludes the `eidos` CLI.
* `AGENTS.md` contains a clean, realistic ~50-line developer guide (high-level `src/eidos/` package overview, how to run `pytest`, type-checking/formatting conventions, and general instructions to keep tests passing).
* Why we do **not** auto-compile `eidos/` into a massive static `AGENTS.md` + 50 ADR files for `Arm A`:
  1. That structured catalog of 40+ C4 components, 45 test-bound invariants, and embedded `DEC-*` rejected alternatives only exists *because* Eidos enforced its creation and maintenance.
  2. Handing `Arm A` a machine-compiled dump of `eidos/` would credit the baseline with Eidos's specification authoring work while still failing to test a realistic developer baseline.

=== 2.2 In-Trajectory Attribution: Separating Discovery vs. Drift Gate inside `Arm B`

We do not need a third or fourth agent arm to separate the value of **Eidos Discovery (`eidos context` / `index`)** from **Eidos Enforcement (`eidos drift` / `validate`)**. Because Antigravity records every step in `.system_generated/logs/transcript.jsonl`, we extract two internal checkpoints from every `Arm B` run:

1. **Checkpoint 1 — Pre-Gate Draft (`Discovery Attribution`)**:
   * Measured up to the moment `Arm B` finishes its initial code/test edits and invokes `eidos drift` (or `eidos validate`) for the first time.
   * Comparing **`Arm B @ Checkpoint 1` vs. `Arm A Final`** isolates pure **Discovery Lift**:
     - How many fewer exploratory tool calls and input tokens did `Arm B` spend before its first edit?
     - Did `eidos context` and `eidos index blast-radius` prevent `DEC-*`/`POL-*` violations and find all downstream callers on the first pass *before* `eidos drift` even ran?
2. **Checkpoint 2 — Post-Gate Final (`Drift Gate Attribution`)**:
   * Measured from the first `eidos drift` invocation to the end of `Arm B`'s turn.
   * Comparing **`Arm B @ Checkpoint 1` vs. `Arm B @ Checkpoint 2`** isolates pure **Enforcement / Self-Healing Lift**:
     - How often did `eidos drift --uncommitted` catch an omitted contract update (`CTR-*`), stale removed symbol (`stale_removed_symbol`), unlinked `INV-*` test binding, or unmapped file at Checkpoint 1 that the agent then fixed autonomously by Checkpoint 2?

== 3. Benchmark Task Taxonomy ($N = 20$ Tasks + 5-Step Chain)

Tasks are constructed against the latest Eidos engine (`v0.21.0`) across four distinct engineering archetypes (5 tasks per archetype), plus one longitudinal 5-step chain.

[IMPORTANT]
====
*Prompt Neutrality Rule (Fairness Across Arms)*:
Every task prompt given to `Arm A` and `Arm B` must be **100% Eidos-agnostic**—written strictly in terms of user-visible product behavior or engineering requirements (e.g., *"Add a `--format sarif` option to the drift CLI report"*), never mentioning `CMP-*`, `CTR-*`, `INV-*`, or `eidos/` paths in the prompt. This ensures `Arm A` is never penalized by unfamiliar specification jargon and `Arm B` must discover the governing specs on its own.
====

=== Archetype 1: Architectural Guardrail & Decision Traps (`5 Tasks`)
* **Design**: The prompt asks for a realistic feature or optimization where the most obvious, idiomatic implementation violates an existing system policy (`POL-*`) or re-implements a design alternative explicitly rejected in an owning spec's `decisions:` (`DEC-*`) block.
* **Concrete Examples**:
  1. *Task 1.1 (`POL-004` Trap)*: "Add automatic natural-language summarization of git diffs when scaffolding a SpecDelta." *(Trap: Calling an external LLM API or SDK violates `POL-004-ZERO-AI-CALL-DEPENDENCY`; must use deterministic local AST/diff extraction.)*
  2. *Task 1.2 (`DEC-INDEX-HYBRID-SEMANTIC-RRF` Trap)*: "Optimize CPU semantic embedding throughput by switching the default ONNX model to `model_fp16.onnx` and left-padding tokenized batches." *(Trap: `EXP-2026-009` / `DEC-INDEX-HYBRID-SEMANTIC-RRF` proved `model_fp16.onnx` triggers a `3.6x` x86_64 emulation slowdown and left-padding collapses batch cosine similarity to `0.004129`.)*
  3. *Task 1.3 (`DEC-VCS-STATIC-TEST-BINDING` Trap)*: "Enhance `eidos validate` so it executes `pytest` on every `INV-*` `test_binding` to confirm the test passes." *(Trap: Violates the architectural decision keeping `eidos validate` a deterministic sub-second static analyzer rather than a test runner.)*
* **What It Measures**: Whether `eidos context -f/-t` surfaces the governing `DEC-*` / `POL-*` guardrail before code is written, preventing the agent from implementing a forbidden design.

=== Archetype 2: Transitive Blast-Radius & Contract Parity (`5 Tasks`)
* **Design**: The prompt requests a signature, schema, or CLI flag change on a foundational module that has 1-hop and 2-hop downstream consumers across multiple packages (`src/eidos/cli`, `src/eidos/core`, `src/eidos/vcs`, `src/eidos/portal`).
* **Concrete Examples**:
  1. *Task 2.1 (CLI Contract Evolution)*: Add or modify a CLI option on an `eidos` subcommand (governed in `Arm B` by `CTR-CLI-SPEC` `cli_args` bidirectional parity) and consumed by downstream hook/portal callers.
  2. *Task 2.2 (Schema & Validator Ripple)*: Add a new constrained property to a v1 JSON Schema under `assets/schemas/v1/` and update scaffolder templates, `SpecValidator`, and `ArchitecturalIndex` sync extraction.
  3. *Task 2.3 (Public Surface Refactor)*: Rename or split a public method on `DeltaEngine` or `ArchitecturalIndex` referenced across `src/eidos/cli/`, `src/eidos/vcs/`, and `src/eidos/portal/`.
* **What It Measures**:
  - **First-Pass Blast-Radius Recall**: Does the agent identify all downstream callers before running tests (via `eidos index blast-radius` and `find-symbol`), or does it edit 1 file and discover breakage through repeated test failures?
  - **Contract & Surface Synchronization (`Arm B`)**: Does `eidos drift` ensure `CTR-*` parity and `== Public Surface` accuracy?

=== Archetype 3: Invariant-Governed Behavioral Changes (`5 Tasks`)
* **Design**: The prompt modifies core domain logic in `src/eidos/vcs/` or `src/eidos/core/` governed by one or more critical behavioral invariants.
* **Concrete Examples**:
  1. *Task 3.1*: Extend `detect_drift` boundary-symbol or strict body-drift checks while preserving existing behavioral guarantees and adding a regression test.
  2. *Task 3.2*: Modify `DeltaEngine.verify_delta` post-condition evaluation (`expect.frontmatter` / `expect.body`) while preserving modification-evidence guarantees (`INV-DELTA-VERIFY-MODIFICATION-EVIDENCE`).
* **What It Measures**: Existing invariant survival, regression test rigor, and how often `eidos drift` catches missing test bindings in `Arm B` before turn completion.

=== Archetype 4: Cold-Start Brownfield Localization (`5 Tasks`)
* **Design**: The prompt describes a subtle symptom or behavior conceptually (using zero exact file names or class names, similar to `HOLD_V2` in `EXP-2026-009`) and asks for a surgical fix.
* **What It Measures**: Pure navigation efficiency—how many tool calls, file reads, and input tokens are spent locating the exact `file:line` when using `eidos index repo-map` + `eidos index search` + `eidos context` vs. raw `grep`/`find`.

=== Longitudinal Chain: The 5-PR Evolution Sequence ($T_1 \to T_5$)
* **Design**: Instead of resetting the worktree between tasks, a sequence of 5 dependent engineering prompts is applied cumulatively on the same branch in both `Arm A` and `Arm B`:
  - $T_1$: Extract a new dedicated module/class from an existing package and document its public API.
  - $T_2$: Add a CLI flag and wire it into the extracted module under a specific performance/caching constraint.
  - $T_3$: Rename the module's primary entry point and remove the legacy signature.
  - $T_4$: Implement a consumer in a second package that calls the updated module and must honor the $T_2$ constraint.
  - $T_5$: Add an end-to-end validation rule and regression test across the $T_1\text{–}T_4$ pipeline.
* **What It Measures**: How `Arm A` accumulates undocumented architectural drift across $T_1\text{–}T_3$ (leading to stale assumptions or broken constraints in $T_4\text{–}T_5$), while `Arm B`'s `eidos drift` gate forces `eidos/` and `index.db` to stay 100% synchronized at every step.

== 4. Deterministic Grading Oracle & Transcript Telemetry

In accordance with `POL-004` (Zero AI Call Dependency), **Eidos-Bench uses zero LLM-as-a-judge grading**. Every subagent run is scored deterministically across 6 metrics:

[cols="1,2,3", options="header"]
|===
| Metric Category | Metric Name | Deterministic Formula / Source

| **1. Functional & Architectural Pass Rate**
| `Pass@1_Composite`
| `1` iff the held-out behavioral `pytest` suite passes (`Pass@1_Func == 1`) AND the deterministic AST boundary/policy audit passes (`Pass@1_Arch == 1`).

| **2. Guardrail Adherence**
| `Hidden_Constraint_Survival`
| `%` of tasks where the final code respects all governing `POL-*` policies, `DEC-*` rejected alternatives, and C4 container import boundaries (verified via AST inspection on both `Arm A` and `Arm B`).

| **3. Navigation Efficiency**
| `Pre_Edit_Tokens` & `Pre_Edit_Calls`
| Cumulative tool-call count and characters/tokens read *prior* to the first `edit_file` / `write_file` call (parsed directly from `.system_generated/logs/transcript.jsonl`).

| **4. Blast-Radius Precision**
| `First_Pass_File_Recall`
| Fraction of ground-truth impacted source files modified *before* the subagent's first `pytest` or `eidos drift` failure.

| **5. Drift Gate Self-Healing (`Arm B`)**
| `Drift_Rescue_Rate`
| Fraction of `Arm B` tasks where Checkpoint 1 (`first eidos drift call`) flagged an error (`drift_detected: true` or validation error) that the agent autonomously resolved by Checkpoint 2 (`turn completion`).

| **6. Longitudinal Fidelity ($T_1 \to T_5$)**
| `Chain_Survival@T_k`
| Task pass rate and documentation-to-AST symbol parity at each sequential step $T_1 \dots T_5$.
|===

== 5. Contamination Controls & Antigravity Subagent Isolation

When running `Arm A` and `Arm B` inside Antigravity on Eidos's own codebase, four isolation controls are critical:

1. **Subagent System-Prompt & CLI Isolation (`define_subagent`)**:
   * In Antigravity, subagents running in the workspace inherit `<user_rules>` (`AGENTS.md`) and the host `PATH`.
   * To prevent `Arm A` from using Eidos tools or reading `/workspaces/eidos`:
     - `bench-arm-a-baseline` is defined via `define_subagent` with an explicit rule override instructing it to operate strictly inside `/tmp/eidos-bench/<task_id>/arm_a`, never access `/workspaces/eidos`, and never run `eidos` CLI commands.
     - In `arm_a` shells, a shim `/tmp/eidos-bench/arm_a_bin/eidos` prepended to `PATH` exits with `127 (eidos: command not found in baseline arm)`, and the transcript parser asserts `0` `eidos` invocations in `Arm A`.
     - `bench-arm-b-eidos` operates strictly inside `/tmp/eidos-bench/<task_id>/arm_b` with full access to `eidos` (`v0.21.0`) and `.agents/plugins/eidos/skills/`.
2. **Dogfood Test Pruning in `Arm A`**:
   * Because Eidos dogfoods its own living specifications (`eidos/`), any test in `tests/` that asserts the existence of the repository's own `eidos/*.adoc` catalog (as opposed to temporary `tmp_path` test fixtures) would artificially fail in `Arm A` when `eidos/` is stripped. The worktree provisioner excludes repo-dogfood spec tests in `Arm A` so `pytest` runs 100% green at $t = 0$ in both arms.
3. **Orphan Worktree Isolation (Zero Git-Log Leakage)**:
   * Each worktree is initialized outside `/workspaces/eidos` (`/tmp/eidos-bench/<task_id>/arm_{a,b}`) as a single squashed orphan commit (`git init` + `git add .` + `git commit -m "Initial commit"`), with no remote or reflog. Running `git log` or `git blame` reveals zero prior commit history.
4. **External Latest Engine Pinning (`v0.21.0+`)**:
   * The grading oracle runs from the host `/workspaces/eidos` (`v0.21.0`) environment against the completed worktree after the subagent finishes.

== 6. Empirical Execution & Results (Spikes 1–3)

=== 6.1 Spike 1 (`spike-antigravity-worktree-harness`): Orphan Worktree & Subagent Isolation

We implemented the automated worktree provisioner (`synthesizer.py`) and paired Antigravity subagents (`bench-arm-a-baseline` and `bench-arm-b-eidos`):

* **Orphan Git Worktree Provisioning**: Each task materializes `/tmp/eidos-bench/<task_id>/arm_a` and `/tmp/eidos-bench/<task_id>/arm_b` as single-commit orphan Git repositories (`git init -b main && git add -A && git commit -m "Initial commit"`), eliminating `git log` / `git blame` history leakage (`1` commit visible in `git log`).
* **Baseline Dogfood Pruning (`Arm A`)**: In `arm_a`, root `eidos/` and `.agents/` are removed, a realistic 50-line developer `AGENTS.md` is written, and `tests/conftest.py` skips tests that assert against Eidos's own live `eidos/*.adoc` catalog when `eidos/` is absent. At $t = 0$, `pytest` runs **`338 passed, 74 skipped, 0 failed`** in `arm_a` and **`412 passed, 0 failed`** in `arm_b`.
* **Zero Cross-Arm Contamination**: Across all 6 live `Arm A` subagent transcripts (`cad1a8f6`, `8749290e`, `2dd3c9a4`, `a3640a41`, `25a3180a`, `fe0c58e7`), `eidos_discovery_calls == 0` and `eidos_drift_calls == 0` (`100.0%` CLI and workspace isolation).

=== 6.4 Key Architectural Takeaways

1. **Where Eidos Delivers Immediate Net Speedup (`T1_4` & `CHAIN_T2`)**:
   * When architectural rationale (`DEC-*`) or multi-component blast radius is non-obvious from a single source file:
     - In `T1_4`, `src/eidos/core/lifecycle/audit.py` contained zero inline comments explaining *why* `git ls-files` is prohibited. `Arm B` (`85d84c14`) ran `eidos context -f src/eidos/core/lifecycle/audit.py --tier deep --json` on Turn 2 and immediately retrieved `DEC-AUDIT-INDEX-SCOPED-DISCOVERY`, cutting pre-edit tool calls by **`-31.3%` (`11` vs. `16`)** and pre-edit tokens by **`-26.6%` (`10,369` vs. `14,132`)** compared to `Arm A` (`25a3180a`), which had to grep across `tests/` and `docs/concepts/*.md`.
     - In `CHAIN_T2` (renaming `include_decisions` -> `with_decisions` across 3 components, CLI contract, and tests), `Arm B` (`a10b246c`) completed the entire code + test + 4-spec refactor in **`33` total tool calls vs. `36` in `Arm A` (`fe0c58e7`)**.
2. **Where Eidos Prevents Silent Downstream Breakage (`T2_1` & `T4_1`)**:
   * In `T2_1`, `Arm A` (`8749290e`) modified `context_command.py` and `context.py` and passed `tests/test_context.py`, but missed `ArchitecturalIndex.get_tiered_context_slice` in `graph_index.py` and broke `tests/fixtures/cli_command_tree.json` (`test_cli_command_groups_help_and_subapps`).
   * In `Arm B` (`94894e7d`), `eidos drift --uncommitted --json` at Step 48 (`Checkpoint 1`) caught the 3 modified components (`CMP-CLI-CONTEXT-COMMAND`, `CMP-TIERED-CONTEXT-COMPRESSOR`, `CMP-GRAPH-STORAGE`) lacking spec co-evolution, and `eidos validate` verified `CTR-EIDOS-CLI` `cli_args` parity, driving a complete self-healing rescue by Step 74 (`Checkpoint 2`).
3. **Why Static `AGENTS.md` Rots Even at $t = 0$ (`T2_1` & `T4_1`)**:
   * The realistic ~50-line `AGENTS.md` in `Arm A` listed `src/eidos/cli/context.py` (the pre-`DLT-2026-052` filename before it was split into `src/eidos/cli/context_command.py`). Both `T2_1 Arm A` and `T4_1 Arm A` failed their first `read_file` call on non-existent `src/eidos/cli/context.py`. Because `Arm B` discovers files through the AST-synced `index.db` (`eidos index find-symbol` / `eidos context`), it experienced zero stale-path errors.
4. **Why `Arm B` Uses More Tokens on Trivial 1-File Edits (`The Co-Evolution Tax`)**:
   * On localized 1-file tasks (`T3_1`, `T4_1`, `T1_1` where `invariants.py` already had an inline comment mentioning `DEC-VCS-STATIC-TEST-BINDING`), `Arm B` used `25–48` total tool calls vs. `15–31` in `Arm A`.
   * Transcript decomposition shows this overhead comes from reading `.agents/plugins/eidos/skills/eidos/SKILL.md`, reading/editing the owning `.adoc` component spec, and running `eidos validate` + `eidos drift`. This is a deliberate **co-evolution tax**: `Arm A` finishes 1-file edits faster precisely because it leaves documentation and architecture specs un-updated (`0/6` spec parity), which is the exact mechanism that causes multi-PR architectural drift.
