== 1. Problem Statement & Baseline Audit

Eidos enforces a strict **Zero AI-Call Dependency (`POL-004-ZERO-AI-CALL-DEPENDENCY`)**: every CLI command must execute deterministically offline with zero LLM API calls, zero neural model weights (`onnxruntime`, `torch`, `sentence-transformers`), and zero external daemons.

Currently, two core workflows rely on purely lexical or path-based matching:

1. **Task-Driven Context Slicing (`eidos context --task "..."` & `eidos index search`):**
   `ArchitecturalIndex.query_fts` (delegating to `execute_fts_search` in `src/eidos/core/index/query.py`) and `build_tiered_context_slice` (`src/eidos/core/index/context.py`) originally tokenized the prompt with `re.findall(r"\w+", text.lower())` and executed an unweighted `OR` prefix query (`"term1"* OR "term2"*`) against the `specs_fts` FTS5 virtual table (`porter unicode61`). _(Pre-fix behavior; see section 3.4.)_
2. **Drift Detection & Living Spec Verification (`eidos drift` & `eidos validate`):**
   `src/eidos/vcs/drift.py` maps modified files to owning containers/components strictly via path globs (`package_path`, `source_path`, `owned_path`) and verifies invariant coverage solely by explicit `INV-*` string markers. It cannot suggest candidate `INV-*` rules for newly written, unbound test functions, nor can it flag semantically duplicate invariants or capabilities across domains.

=== 1.1 Structural Bottlenecks Discovered in `specs_fts` & `build_tiered_context_slice`

During Spike 1 and the 2026-10-16 audit across `src/eidos/core/index/` (`sync.py`, `query.py`, `context.py`), we identified and fixed six concrete retrieval and slice-assembly bottlenecks:

1. **Historical `DLT-*` Slot Starvation** — *FIXED (`DLT-2026-053`):*
   `specs_fts` indexes all applied historical `delta/mutation` (`DLT-*`) records alongside active architecture specs. When `build_tiered_context_slice` queried `query_fts(task, limit=8)` without a SQL-level type filter, up to 5 of the 8 top BM25 slots were consumed by historical `DLT-*` documents and discarded—starving the slice of relevant containers and capabilities.
2. **Missing Child `invariant` (`INV-*`) FTS Rows** — *FIXED (`DLT-2026-053`):*
   While child `INV-*` rules were extracted into the `entities` table, they were **never inserted into `specs_fts`** (only the parent document was): 97 FTS rows for 136 entities, the gap being the 39 invariants. Consequently, `elif etype == "invariant":` in `build_tiered_context_slice` was dead code for direct lexical matches.
3. **Compound Identifiers (`snake_case` & `camelCase`)** — *FIXED (`DLT-2026-053`); original claim corrected:*
   _Correction:_ `unicode61` *does* split `snake_case` on the index side (`_` is a separator). The real defects were (a) the query side: `\w+` keeps `detect_drift` whole, and FTS5 re-tokenizes a quoted `"detect_drift"*` into an *order-sensitive phrase* (`detect drift`), so it never matches "drift detection"; and (b) `camelCase` identifiers (`ArchitecturalIndex`) stay atomic, so only their leading sub-token is reachable via prefix matching. Persisted AST `code_symbols` are still not projected into `specs_fts.symbols` (open).
4. **Unweighted FTS Columns & Zero Synonym Expansion** — *weights FIXED (`DLT-2026-053`, neutral, see 3.4); synonyms open:*
   `bm25(specs_fts)` weights a match in a 500-word `body_text` prose section equally with a match in `title` or `keywords`, and fails when a user prompt uses domain synonyms (e.g., *"zero llm offline execution"* vs. `POL-004-ZERO-AI-CALL-DEPENDENCY`).
5. **Dropped Domain / Design-System Matches** — *FIXED (`DLT-2026-053`):*
   `build_tiered_context_slice` had no branch for `product/domain` or `design/system`, so FTS hits on `DOM-*` / `DS-*` were silently discarded. They now expand to their member containers and capabilities (`domain_member`, `styles_container` edges), and the matched ID is kept in `matched_reasons`.
6. **Alphabetical `direct_inv_ids` Sorting, 1-Hop Budget Crowding & Unpromoted Invariant Parents** — *FIXED (commit `5bfc2a9`):*
   In `src/eidos/core/index/context.py`, `direct_inv_ids` was stored as a Python `set[str]` and iterated via `sorted(direct_inv_ids)` (alphabetical order instead of BM25 rank order), while `_enforce_token_budget` popped tail items without first evicting 1-hop expanded entities or compacting verbose `DEC-*` prose. Under the `1,000`-token `guardrails` budget (`DLT-2026-047`), `#1` BM25 invariant matches (e.g., `INV-HOOK-BLOCK-ONCE`, `INV-REMOVAL-TOMBSTONE`, `INV-INDEX-AI-REPO-MAP-BUDGET`) were evicted in favor of alphabetically earlier `#5`–`#8` matches. In addition, when a child `INV-*` outranked its parent `CAP-*`/`POL-*`, the parent specification was not promoted into `direct_cap_ids`/`direct_pol_ids`. Both are now fixed (`test_inv_context_token_compression`).

== 2. Model-Free Semantic Architecture Under Investigation

To achieve semantic similarity without neural weights or external dependencies, we combine **distributional corpus statistics**, **character/subword random projections**, **information-theoretic compression distance**, and **graph topology** using only Python's standard library (`hashlib`, `math`, `zlib`, `collections`, `sqlite3`).

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                   1. Sync-Time Index Enrichment (<185ms cold)                │
│  ├── De-compound camelCase / snake_case identifiers across Specs + AST       │
│  ├── Index child INV-* entities & AST code_symbols into specs_fts            │
│  ├── Compute Corpus PPMI Co-Occurrence Top-K Neighbors (math.log2)           │
│  └── Project Subword TF-IDF (words + bigrams + char 3/4-grams) via           │
│      blake2b Signed Feature Hashing -> 256-byte int8 BLOB per entity         │
└──────────────────────────────────────┬───────────────────────────────────────┘
                                       │
         ┌─────────────────────────────┴─────────────────────────────┐
         ▼                                                           ▼
┌─────────────────────────────────────────┐ ┌──────────────────────────────────┐
│   Use Case 1: Context Slicing & Search  │ │ Use Case 2: Drift & Validation   │
│   (eidos context -t / index search)     │ │ (eidos drift / eidos validate)   │
├─────────────────────────────────────────┤ ├──────────────────────────────────┤
│ 1. Expand query with top PPMI neighbors │ │ 1. Extract AST diff / unbound    │
│ 2. Scoped Column-Weighted FTS5 BM25     │ │    test function body & symbols  │
│    bm25(specs_fts, 0, 4, 2, 1, 2, 2)    │ │ 2. Score 256-dim Subword Cosine  │
│ 3. 256-dim Subword Hash Vector Cosine   │ │    against candidate INV-*/CAP-* │
│ 4. 1-hop Graph Spreading Activation     │ │ 3. Re-rank top candidates with   │
│    (degree-normalized, α = 0.35)        │ │    stdlib zlib NCD similarity    │
│ 5. Reciprocal Rank Fusion (RRF)         │ │ 4. Emit ranked INV-*/spec advice │
└─────────────────────────────────────────┘ └──────────────────────────────────┘
```

=== 2.1 Technique A: Corpus Pointwise Mutual Information (PPMI) Query Expansion

During `ArchitecturalIndex.sync()`, we extract salient de-compounded tokens from each active specification (`title`, `jtbd_or_rule`, `keywords`, `symbols`, and primary AST `code_symbols`) and compute pairwise co-occurrence probabilities across the repository:

$$\text{PPMI}(w_1, w_2) = \max\left(0, \log_2 \frac{P(w_1, w_2)}{P(w_1) P(w_2)}\right)$$

Retaining the top-$k$ ($k=3$) highest-PPMI neighbors per term (for pairs with count $\ge 2$ and $\text{PPMI} > 1.0$) creates a deterministic, repository-specific thesaurus in `<15ms` during sync. At query time, searching for `"llm"` or `"tree_sitter"` automatically expands into co-occurring architectural vocabulary (`deterministic`, `dependency`, `ast`, `polyglot`, `symbol`).

=== 2.2 Technique B: 256-Dimensional Signed Subword Feature Hashing (Random Projection)

To capture morphological variants, partial identifier overlap, and code-to-spec vocabulary alignment without storing a large vocabulary matrix, every entity $e$ is converted into a stream of weighted subword features:
* **De-compounded word tokens** (`w:<token>`, weight $3\times$)
* **Adjacent token bigrams** (`b:<t1>_<t2>`, weight $2\times$)
* **Boundary-padded character 3-grams and 4-grams** (`c:<ngram>`, weight $1\times$)

Each feature $f$ with term frequency $\text{tf}(f)$ and corpus inverse document frequency $\text{idf}(f) = \ln\left(\frac{N + 1}{\text{df}(f) + 0.5}\right) + 1$ is projected into a fixed $D = 256$ dimensional vector using deterministic `hashlib.blake2b` (4-byte digest) for both bucket index $h(f) \in [0, 256)$ and Rademacher sign $s(f) \in \{-1, +1\}$ (the **Weinberger et al. Signed Feature Hashing** trick, which guarantees an unbiased inner product $\mathbb{E}[\langle \hat{u}, \hat{v} \rangle] = \langle u, v \rangle$):

$$v[h(f)] \mathrel{+}= s(f) \cdot \bigl(1 + \ln \text{tf}(f)\bigr) \cdot \text{idf}(f)$$

After $L_2$ normalization, each float component $v_i \in [-1, 1]$ is quantized to a signed 8-bit integer (`int8`, `round(v_i * 127)`), occupying **exactly 256 bytes per entity** (`33.5 KB` total across all 134 entities in Eidos).

[NOTE]
====
*Review caveats:*

* Unbiasedness holds only in expectation. The variance grows as $\|u\|^2\|v\|^2 / D$, and with tens of thousands of distinct char n-grams per corpus each of the 256 buckets is shared by hundreds of features. A random-pair cosine distribution must be reported as a noise floor before reading scores like `0.48`.
* At about 136 entities, an *exact* sparse TF-IDF over the same features costs a few KB and has no collision noise. It is the required comparator for this technique.
* The bucket and sign bits must be specified (for example, bucket = digest byte 0, sign = low bit of digest byte 1). If vectors are L2-normalized before quantization, a separate `norm` column is redundant.
* IDF (and PPMI in 2.1) are corpus-global statistics. Any spec edit makes every stored vector stale, which conflicts with incremental sync (see section 5).
====

=== 2.3 Technique C: 1-Hop Graph Spreading Activation & Reciprocal Rank Fusion (RRF)

First-stage rankings from **Scoped Column-Weighted FTS5 BM25** (`bm25(specs_fts, 0.0, 4.0, 2.0, 1.0, 2.0, 2.0)`, now shipped, scoped to sliceable types) and **256-dim Subword Cosine Similarity** are combined via Reciprocal Rank Fusion ($k_0 = 12$):

[WARNING]
====
The originally published weights `bm25(specs_fts, 10.0, 6.0, 1.0, 8.0, 6.0)` were *off by one column*. FTS5 assigns weights positionally over *all* columns, including the `UNINDEXED` `entity_id`, so they produced title=6, rule=1, body=8, keywords=6, symbols=1. That boosts long prose, the opposite of the intent. Any RRF result computed with those weights is invalid.
====

$$S_{\text{seed}}(e) = \frac{1.0}{k_0 + \text{rank}_{\text{BM25}}(e)} + \frac{1.1}{k_0 + \text{rank}_{\text{Cosine}}(e)}$$

We then execute a single **1-hop spreading activation** step over the SQLite `edges` table ($\alpha = 0.35$) from the top-6 seed entities. This is not Personalized PageRank (no iteration, no teleport). The formula below lets hub nodes (`POL-004`, `CNT-EIDOS-CORE`) flood the results; the next iteration must divide by node degree ($\deg(v)$) and report precision@8:

$$S_{\text{final}}(u) = S_{\text{seed}}(u) + \alpha \sum_{v \in \mathcal{N}_{\text{top-6}}(u)} S_{\text{seed}}(v)$$

This surfaces structurally coupled domain capabilities (`CAP-*`), governing policies (`POL-*`), and invariants (`INV-*`) even when they share zero words with the user's prompt.

=== 2.4 Technique D: Normalized Compression Distance (NCD) via `zlib` for Drift & Validation

For `eidos drift` and `eidos validate`, we need to compare richer text passages—such as matching an unbound test function (`def test_...` body + assertions) against candidate `INV-*` rules, or auditing two specifications for semantic duplication. We combine Subword Feature Cosine ($0.75$ weight) with information-theoretic **Normalized Compression Distance** ($0.25$ weight) using Python's built-in `zlib.compress`:

$$\text{Sim}_{\text{NCD}}(x, y) = 1 - \frac{C(x \mathbin{\Vert} y) - \min\bigl(C(x), C(y)\bigr)}{\max\bigl(C(x), C(y)\bigr)}$$

where $C(x) = |\text{zlib.compress}(x)|$ approximates Kolmogorov complexity via LZ77+Huffman shared dictionary compression.

[NOTE]
====
*Review caveats:*

* NCD is asymmetric in concatenation order. Use $\min$ or the mean of $C(x \Vert y)$ and $C(y \Vert x)$, and clamp the result to $[0, 1]$.
* Invariant rules are 100–300 characters, so zlib's fixed header and checksum overhead dominates. NCD is unreliable at that length, and the 0.25 weight needs its own ablation.
* Compressed lengths can differ between zlib builds (for example zlib-ng), which would make scores non-reproducible across CI machines (POL-004 determinism).
====

=== 3.3 Why the Original Results Are Withdrawn (2026-10-15 Review)

1. *No ablation.* 4 of the 7 baseline misses were `INV-*` entities that were never indexed. The other 3 were all in
   one query that was hurt by SpecDelta crowding. A fixed lexical baseline was never measured, so the gain could
   not be credited to PPMI, hashing, the graph step, or NCD.
2. *The weights were invalid.* The published BM25 weights were shifted by one column (see the warning in 2.3).
3. *The metric was not slice recall.* `get_tiered_context_slice` dropped `product/domain` and `design/system` hits,
   so 2 of the 18 targets (`DOM-VCS-LIFECYCLE`, `DS-CORE`) could never appear in a real slice. The reported 18/18
   must have been measured on a raw ranked list. Real slice recall was at most 16/18 (88.9%), below the bar.
4. *The sample was too small and was used for tuning.* The 95% Wilson lower bound for 18/18 is 82.4%, below the
   90% criterion. For the test-to-invariant result (29/39 = 74.4%) the interval is [58.9%, 85.4%], so it does not
   clearly clear 70%. About 10 hyperparameters appear to have been tuned on the same 6 prompts.
5. *The criteria changed after the fact.* The query budget was < 2 ms in Q2 and < 3 ms elsewhere; storage was
   < 50 KB vs < 64 KB. The sync (< 250 ms) and near-duplicate scan (< 20 ms) criteria were added in section 3.2 and
   never declared in the frontmatter. The near-duplicate scan reported only latency, with no quality metric.

=== 3.4 Spike: Baseline-Fix & Context-Slice Budget Ablation (DONE, 2026-10-16, commit `5bfc2a9`)

The four FTS coverage fixes (child `INV-*` FTS rows, a slice-scoped type filter applied inside SQL before `LIMIT`,
identifier de-compounding on both the index and query sides, and positional column weights `(0, 4, 2, 1, 2, 2)`)
shipped under `DEC-INDEX-FTS-RETRIEVAL-HYGIENE` (`CNT-EIDOS-INDEX`, `DLT-2026-053`, index `SCHEMA_VERSION` 2.3.0),
guarded by `INV-AGENT-TASK-RETRIEVAL-COVERAGE` (`tests/test_graph_index.py::test_task_retrieval_indexes_invariants_and_filters_types`).
The three context-slice assembly fixes (BM25 rank-order preservation for `direct_inv_ids` and `direct_ctr_ids`,
two-stage token-budget eviction, and invariant parent `capability_id`/`policy_id` promotion) shipped in commit
`5bfc2a9`, guarded by `INV-CONTEXT-TOKEN-COMPRESSION` (`tests/test_context.py::test_inv_context_token_compression`).

*Method.* The benchmark builds an isolated index in a temporary directory (so `eidos/.cache/index.db` is never touched)
against pinned commit `5bfc2a9`. It measures:

1. **Raw `Recall@8`** over the ranked candidates that feed the slice (`TASK_SLICE_ENTITY_TYPES`), and
2. **End-to-end `guardrails` slice recall ($\le 1,000$ tokens)** from `get_tiered_context_slice(tier="guardrails")`
   (a target counts if it is present in any slice list or as a `matched_reasons` key), plus mean slice entity count as
   a precision proxy.

* *DEV* = the 6 published prompts above (18 targets), originally used to tune the superseded hybrid prototype.
* *HOLD* = 12 prompts (28 targets) written before any post-fix measurement. Because `HOLD` was later inspected to

*Findings:*

* **Raw FTS Recall@8:** The shipped lexical baseline reaches 39/46 = *84.8%* combined (95% Wilson CI [71.8%, 92.4%]),
  up from 19/46 = 41.3% [28.3%, 55.7%]. Mean query latency is 0.48 ms (DEV) and 1.00 ms (HOLD). Most of the gain comes
  from *child invariant FTS rows* and the *SQL type filter*; de-compounding helps on identifier-heavy DEV prompts;
  positional column weights are neutral on both sets.
* **End-to-End Budgeted Slice Recall & Precision:** Preserving BM25 rank order across `direct_inv_ids` and
  `direct_ctr_ids`, evicting 1-hop expanded entities and verbose `DEC-*` prose before direct matches, and promoting the
  owning `capability_id`/`policy_id` of directly matched invariants achieves **17/18 (`94.4%`) on DEV** and **26/28
  (`92.9%`) on HOLD** while compressing mean slice size from ~40 entities down to **7.5 (DEV) and 8.6 (HOLD)** within

* **Cost:** Cold sync +40 ms (~438 ms to ~472 ms, including AST indexing). There are no new tables, vectors, or global
  statistics, so incremental sync (<5 ms) is unaffected.
* **Remaining Gap:** Across all 46 targets in DEV + HOLD, only 3 misses remain in the final slice (`DOM-VCS-LIFECYCLE`
  on DEV; `INV-COMPONENT-CENTRALIZATION-MANDATE` and `CNT-EIDOS-DOCS` on HOLD), and only ~1 looks like genuine
  vocabulary mismatch. Any future statistical/vector experiment must evaluate against a fresh held-out query set
  (`HOLD_V2`, $\ge 30$ prompts).
* **Corpus Drift:** Numbers move slightly as living specs evolve. Benchmarks must pin a corpus snapshot (commit SHA
  `5bfc2a9`).

== 4. Target Integration Architecture

=== 4.1 Integration Point 1: `CNT-EIDOS-INDEX` Submodules (`src/eidos/core/index/`)

Following the `DLT-2026-052` decomposition of `ArchitecturalIndex` (`graph_index.py`) into focused C4 components:

1. **`CMP-GRAPH-STORAGE` (`storage.py`) & `CMP-INCREMENTAL-SYNC-ENGINE` (`sync.py`):**
   * *SHIPPED (`SCHEMA_VERSION` 2.3.0, `DLT-2026-053`):* child `invariant` (`INV-*`) entities are indexed in `specs_fts` (purged with their parent spec via `delete_spec_fts_rows` on incremental sync), and de-compounded `camelCase`/`snake_case` sub-tokens are added to `specs_fts.symbols`. *Open:* projecting primary AST `code_symbols` into `specs_fts.symbols` after `reconcile_code_ownership`.
   * *CONTINGENT on section 5:* a lightweight `semantic_vectors` table (`entity_id TEXT PRIMARY KEY, vec_int8 BLOB NOT NULL`) and a `ppmi_terms` table (`term TEXT, neighbor TEXT, ppmi REAL`). Corpus-global IDF and PPMI cannot be updated per-file without a staleness strategy (see section 5).
2. **`CMP-FTS-QUERY-ENGINE` (`query.py`) & `CMP-TIERED-CONTEXT-COMPRESSOR` (`context.py`):**
   * *SHIPPED (`DLT-2026-053`):* `execute_fts_search(..., include_types=None, exclude_types=())` with filters applied inside SQL before `LIMIT`, identifier sub-token splitting (`_split_identifier_subtokens`), positional column-weighted BM25 `bm25(specs_fts, 0.0, 4.0, 2.0, 1.0, 2.0, 2.0)`, and deterministic `e.id` tie-breaking. `build_tiered_context_slice` passes `include_types=TASK_SLICE_ENTITY_TYPES` and expands matched `DOM-*` / `DS-*` entities to member containers and capabilities.
   * *SHIPPED (`DLT-2026-047` & commit `5bfc2a9`):* `TieredContextSlice` enforces strict token budgets across Markdown and JSON (`to_dict`), preserves BM25 insertion rank order for `direct_inv_ids` and `direct_ctr_ids`, promotes the owning `capability_id` and `policy_id` of directly matched invariants, and executes two-stage budget eviction (trimming 1-hop expansions and compacting decision prose before evicting direct matches).
   * *CONTINGENT:* PPMI query expansion, 256-dim `int8` subword vector cosine scoring, and degree-normalized 1-hop graph spreading activation fused via RRF. Adopted only if a layer beats the shipped `5bfc2a9` baseline on `HOLD_V2`.

=== 4.2 Integration Point 2: `detect_drift` (`src/eidos/vcs/drift.py`) — all CONTINGENT

1. **Semantic Diff-to-Spec Ranking in `eidos drift`:**
   * Extract added/modified identifiers, docstrings, and diff hunks from modified `code_files` and rank candidate capabilities (`CAP-*`), contracts (`CTR-*`), and invariants (`INV-*`) using the Hybrid Subword Cosine + `zlib` NCD scorer instead of listing all 1-hop neighbors unranked.
2. **Unbound Test-to-Invariant Advisor in `eidos drift`:**
   * When an uncovered `INV-*` or a newly added test function (`test_*`) without an `INV-*` marker is detected, compute top-3 semantic matches using Subword Cosine + `zlib` NCD and include concrete binding suggestions in `remediation_suggestions`.
   * About 26% of top-3 suggestions were wrong in the withdrawn spike. Suggestions must stay *advisory*: they must never change `drift` / `lint` exit codes or `is_clean`.
3. **Near-Duplicate Invariant / Spec Warning in `eidos validate` / `eidos hook lint`:**
   * Flag invariant or capability pairs whose hybrid Cosine + NCD similarity exceeds a high threshold ($\ge 0.80$) to prevent redundant or conflicting architectural rules. The threshold must first be calibrated on labelled duplicate and non-duplicate pairs.
4. New JSON fields (`remediation_suggestions` content, richer `matched_reasons`) change the CLI JSON envelope. They must be declared as a `CTR-EIDOS-CLI` version bump in the resulting SpecDelta.
