= Exploration: Evaluating a Minimalist Model Context Protocol (MCP) Bridge for Guaranteed Agent Tool Invocation
:toc: left
:icons: font
:sectnums:

== 1. Problem Statement & Operational Observations

In `DLT-2026-016`, Eidos formally deprecated and decommissioned its original Model Context Protocol daemon (legacy MCP container and contract in `src/eidos/mcp/`) in favor of direct CLI commands (`eidos <cmd> --json`) and progressive disclosure via Agent Skills (`SKILL.md`).

The rationale behind `DLT-2026-016` remains technically sound:
1. **Prompt Overhead:** The original 17-tool MCP catalog injected 2,500–3,500 tokens of JSON Schema into every turn.
2. **Dual-Surface Debt:** Maintaining dual implementations in `src/eidos/cli/` and `src/eidos/mcp/` created subtle divergence.
3. **Daemon Fragility:** Background stdio daemons suffered from buffer desynchronization, zombie processes, and IDE restart hangs.

=== 1.1 The Emerging Failure Mode: The "Passive Skill" Dilemma

Despite the elegance of CLI + Progressive Skills, empirical observation of autonomous AI agents (Google Antigravity, Claude Code, Cursor, Copilot) in real-world workflows reveals a significant behavioral gap:

[quote, Operational Finding]
____
Autonomous AI agents frequently neglect or fail to take full advantage of the Eidos CLI during normal coding loops.
____

This behavioral failure stems from three concrete architectural factors:

1. **Passive Skill Discovery Failure:**
   Agent Skills (`SKILL.md`) rely on the agent's LLM router reading a high-level description and proactively loading the skill. When a developer prompts an agent with a routine task (*"fix the parsing bug in parser.py"* or *"optimize the SQL query"*), the LLM's classification layer categorizes it as a local code fix rather than an architectural event. Consequently, the agent **never loads `eidos/SKILL.md`**, and never learns to run `eidos context` or `eidos drift`.
2. **Tool Palette Structural Bias:**
   LLMs are heavily fine-tuned to prefer their **native first-class tool palette** (`view_file`, `replace_file_content`, `grep_search`). Using the Eidos CLI requires the model to formulate a subshell call (`run_command` or `bash`). Without explicit prompting, models default to raw file viewing and heuristic editing, bypassing Eidos's AST knowledge graph and invariant checks.
3. **Absence of Forced Feedback Loops:**
   Unless an active drift gate or pre-commit hook aborts the agent's turn, an agent can complete entire multi-file refactors without ever running `eidos drift`, leaving living specifications unmaintained and silently decaying.

== 2. Hypotheses & Proposed Architectural Model

Instead of an all-or-nothing dichotomy between *No MCP* and *Monolithic 17-Tool MCP Daemon*, we hypothesize that a **hybrid architecture** provides the optimal balance.

│   │ (3 Curated MCP Tools)    │         │ (Specialized Guidelines)  │   │
│   │                          │         │                           │   │

=== 2.1 The Minimalist 3-Tool Surface

By exposing strictly three essential governance tools, prompt overhead remains negligible while guaranteeing discovery:

1. **`eidos_context`**:
   - *Inputs:* `file?: string`, `task?: string`, `tier?: "anchor" | "guardrails" | "deep"`
   - *Behavior:* Returns token-budgeted architectural context slice directly into tool response.
2. **`eidos_drift`**:
   - *Inputs:* `uncommitted?: boolean`, `base_ref?: string`
   - *Behavior:* Returns Git spec-to-code drift status, affected components, and remediation actions.
3. **`eidos_validate`**:
   - *Inputs:* `path?: string`
   - *Behavior:* Validates `.adoc` specifications against JSON Schemas and reports errors.

All complex lifecycle actions (scaffolding explorations, managing SpecDeltas, running migration changelogs) remain cleanly in the CLI and progressive skills.

=== 2.2 Core Architectural Principles for the MCP Bridge

To prevent repeating the architectural failures of the legacy MCP implementation, any new MCP component must adhere to:

* **Zero Duplication (Strict Thin Wrapper):** The MCP handler must not implement any validation, drift, or context logic. It must be a thin transport layer (`src/eidos/cli/mcp.py` or `src/eidos/mcp/`) that calls existing CLI controller functions and returns the exact same Pydantic/JSON models.
* **Ephemeral Stdio Lifecycle:** No persistent background daemon state or separate process management. The server starts instantly on stdio per session and shuts down cleanly.
* **Strict Token Budget (< 400 Tokens):** The cumulative tool definitions for all 3 tools must not exceed 400 tokens of JSON Schema in the model prompt.
* **POL-004 Determinism:** 100% deterministic local execution, zero LLM calls inside the engine.

== 3. Investigation & Empirical Spikes

=== Spike 1: Agent Compliance Benchmark (`spike-agent-compliance-baseline`)
Evaluate agent invocation compliance across 20 common software engineering prompts (5 bug fixes, 5 refactors, 5 feature additions, 5 test updates) under three isolated configurations:

* **Config A (Current Baseline):** Passive Agent Skills only (`.agents/plugins/eidos/skills/`).
* **Config B (Rules-Enhanced):** Passive Skills + Mandatory Workspace Rule (`AGENTS.md` / `.cursorrules`).
* **Config C (Hybrid 3-Tool MCP):** 3-Tool MCP Bridge active in agent tool palette.

*Metrics to capture:*
* % of tasks where architectural context was extracted prior to code edits.
* % of tasks where drift verification was executed prior to completion.
* Total prompt token overhead per turn.

=== Spike 2: Token Overhead & Schema Audit (`spike-minimalist-mcp-schema-audit`)
Measure exact BPE token counts for:
* Legacy 17-tool MCP schema catalog (`~2,850` tokens).
* Proposed 3-tool minimal schema catalog (`eidos_context`, `eidos_drift`, `eidos_validate`).
* Comparison with raw `SKILL.md` system injection.

=== Spike 3: Stateless Stdio Prototype (`spike-stateless-stdio-prototype`)
Prototype a zero-dependency stdio JSON-RPC 2.0 dispatcher:
```bash
eidos mcp serve
```
Verify cold start latency is `< 50ms`, memory consumption is `< 20MB`, and tool execution maps 1:1 with `eidos context --format json` and `eidos drift --uncommitted --json`.

== 4. Risks & Mitigations

[cols="1,2,2", options="header"]
|===
| Risk | Impact | Mitigation
| **Dual Maintenance Burden** | CLI and MCP schemas drift out of sync over time. | Generate MCP tool schemas and handler dispatch directly from the shared Typer CLI or core index controller functions.
| **Client Configuration Fragmentation** | Users struggle to configure `.mcp.json` or `claude_desktop_config.json`. | Integrate MCP configuration generation into `eidos plugin install` as an optional flag (`eidos plugin install --with-mcp`).
| **Prompt Bloat Creep** | Temptation to add `eidos_delta_create`, `eidos_spec_delete`, etc., returning to the 2,500-token problem. | Strictly enforce a 3-tool cap in `POL-004` or container invariants.
|===
