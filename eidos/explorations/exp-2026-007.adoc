= Exploration: Evaluating a Minimalist Model Context Protocol (MCP) Bridge for Guaranteed Agent Tool Invocation
:toc: left
:icons: font
:sectnums:

== Core Hypothesis
Reintroducing a minimalist, zero-state Model Context Protocol (MCP) transport wrapper exposing strictly two to three high-impact tools (`eidos_context`, `eidos_drift`, and optionally `eidos_validate`) with a total prompt footprint $\le 400$ tokens will increase autonomous agent compliance for upfront context slicing and mid-loop drift verification from $< 30\%$ to $\ge 90\%$ across coding sessions, while avoiding the 2,500-token prompt bloat and dual-surface maintenance defects that caused the original 17-tool MCP daemon decommissioning under `DLT-2026-016`.

== Questions & Spikes
* **Spikes**:
  - `spike-agent-compliance-baseline`: Audit autonomous agent invocation rates of `SKILL.md`, `eidos context`, `eidos drift`, and `eidos validate` across $n = 95$ real coding sessions (`82` top-level user sessions and `13` delegated subagent sessions) spanning three historical architectural regimes.
  - `spike-minimalist-mcp-schema-audit`: Measure exact token budgets for the legacy MCP catalog (`b4e1c730`), proposed 3-tool MCP catalog (`eidos_context`, `eidos_drift`, `eidos_validate`), deduplicated 2-tool catalog (`eidos_context`, `eidos_drift`), and the 4 consolidated Agent Skills.
  - `spike-stateless-stdio-prototype`: Prototype and benchmark a zero-dependency `orjson` stdio JSON-RPC 2.0 handler (`eidos mcp serve`), measuring cold-start latency (standard Typer import vs. fast-path `sys.argv` dispatch), warm per-RPC latency, resident memory (`VmRSS`), and 1:1 CLI JSON output parity.

== Findings & Learnings
Auditing all $n = 95$ real Eidos coding transcripts (`2026-10-11` to `2026-10-20`) proved that the $< 30\%$ aggregate pre-edit `eidos context` rate (`28/95 = 29.5%`) was an artifact of **pre-`DLT-2026-076` 14-skill fragmentation** (`26.2%` in Regime 1) and **delegated worker subagents** (`15.4%`), NOT passive skill discovery failure. Following `DLT-2026-076` (which consolidated 14 micro-skills into 4 cohesive skills with `eidos/SKILL.md` as master orchestrator) and `DLT-2026-094` (stateless `Stop` hook `eidos hook`), top-level agent sessions (`n = 21`, Regime 2) already achieve **`100.0%` (`21/21`) `SKILL.md` discovery**, **`90.5%` (`19/21`) `eidos drift` compliance** (`93.8%` on non-attachment prompts), **`100.0%` (`21/21`) `drift`/`validate` gate execution**, and **`87.5%` (`14/16`) `eidos context` execution** on tasks requiring architectural discovery—while Spike 3 showed a persistent stdio MCP process holds **`75.89 MB` VmRSS** (`3.8x` over the `< 20 MB` target) and `186.42 ms` Typer cold start. The MCP bridge is therefore **discarded**.

*Status (2026-10-20 — CONCLUDED / DISCARDED on branch `spike/exp-2026-007`):*

1. *Empirical Root-Cause Reversal (Spike 1, $n = 95$ real coding sessions):* The hypothesis assumed agents fail to load `eidos/SKILL.md` during coding tasks. In reality, top-level sessions loaded `SKILL.md` **`91.5%` (`75/82`)** of the time overall and **`100.0%` (`21/21`)** after `DLT-2026-076` consolidated the 14 fragmented skills into 4 skills (`eidos`, `eidos-spec`, `eidos-plan`, `eidos-ops`). Under the current 4-skill + `Stop` hook architecture (Regime 2), `eidos drift` is already **`90.5%` (`19/21`)**, `drift OR validate` is **`100.0%` (`21/21`)**, and `eidos context` on prompts without pre-attached `@[file]` paths is **`87.5%` (`14/16`)**.

3. *Prototype Resource & Cold-Start Violations (Spike 2 & Spike 3):* While a compact 3-tool MCP schema fits in `268` calibrated tokens (`208` tokens for a deduplicated 2-tool schema) and warm `eidos_context` JSON-RPC calls execute in `1.40–1.98 ms`, loading `fast_yaml`, `jsonschema`, `ast_grep_py`, and `sqlite3` into a persistent stdio server holds **`75.89 MB` VmRSS** (`3.8x` over the `< 20 MB` target) for the entire IDE session, and standard Typer CLI startup takes **`186.42 ms`** (`51.29 ms` even with a custom non-Typer `sys.argv` bypass).

== 1. Problem Statement & Operational Observations

In `DLT-2026-016`, Eidos formally deprecated and decommissioned its original Model Context Protocol daemon (legacy MCP container and contract in `src/eidos/mcp/`) in favor of direct CLI commands (`eidos <cmd> --json`) and progressive disclosure via Agent Skills (`SKILL.md`).

The rationale behind `DLT-2026-016` remains technically sound:
1. **Prompt Overhead:** The original MCP catalog injected `2,761–3,798` tokens of JSON Schema into every turn.
2. **Dual-Surface Debt:** Maintaining dual implementations in `src/eidos/cli/` and `src/eidos/mcp/` created subtle divergence.
3. **Daemon Fragility:** Background stdio daemons suffered from buffer desynchronization, zombie processes, and IDE restart hangs.

=== 1.1 The Initial Hypothesis: The "Passive Skill" Dilemma

Prior to ablating the session transcripts by architectural regime, aggregate telemetry across all 95 historical coding sessions showed that `eidos context` was executed prior to the first file edit in only `28/95` (`29.5%`) of sessions. We initially hypothesized three causes:

1. **Passive Skill Discovery Failure:**
   Agent Skills (`SKILL.md`) rely on the agent's LLM router reading a high-level description and proactively loading the skill. We hypothesized that routine prompts caused the agent to skip loading `eidos/SKILL.md`. *(Falsified in Spike 1: top-level sessions loaded `SKILL.md` 91.5% overall and 100.0% post-`DLT-2026-076`.)*
2. **Tool Palette Structural Bias:**
   LLMs are heavily fine-tuned to prefer their native first-class tool palette (`view_file`, `edit_file`, `grep_search`) when a user prompt already attaches explicit `@[file]` paths. *(Confirmed in Spike 1 for `@[file]` review prompts: 40.0% vs. 87.5% when discovery is required.)*
3. **End-of-Turn Feedback vs. Proactive Mid-Loop Grounding:**
   While Eidos ships a stateless `Stop` lifecycle hook (`eidos-drift-gate` invoking `eidos hook`, consolidated in `DLT-2026-087` and `DLT-2026-094`) that runs `detect_drift(uncommitted=True)` at the end of an agent turn, we wanted to measure whether top-level agents already run `eidos drift` proactively before stopping. *(Confirmed in Spike 1: 90.5% in Regime 2 already run `eidos drift` before turn completion.)*

=== 2.1 Candidate Minimalist Tool Surface

1. **`eidos_context`**:
   - *Inputs:* `files?: string[]`, `component?: string`, `task?: string`, `tier?: "anchor" | "guardrails" | "deep"` (mapping 1:1 to `eidos context --file --component --task --tier --json`).
   - *Behavior:* Returns a token-budgeted architectural context slice (`TieredContextSlice.to_json()`).
2. **`eidos_drift`**:
   - *Inputs:* `uncommitted?: boolean`, `base_ref?: string` (mapping 1:1 to `eidos drift --uncommitted --base --json`).
   - *Behavior:* Returns Git spec-to-code drift status, schema validation errors, invariant test-binding coverage, and remediation actions (`DriftVerificationResult`).
3. **`eidos_validate`** *(Redundant with `eidos_drift` per `DLT-2026-094`)*:
   - *Inputs:* `path?: string` (mapping 1:1 to `eidos validate [PATH] --json`).
   - *Behavior:* Validates `.adoc` specifications against v1 JSON Schemas (`ValidationReport`). Because `detect_drift()` already executes `SpecValidator().validate_directory()`, `eidos_validate` duplicates `eidos_drift`.

*Additional Operational Defect Identified in Spike 3:*
* **Workspace Root & Git Worktree Ambiguity:** Unlike CLI commands executed via the agent's subshell (`run_command`), which automatically inherit the active terminal `cwd` (including secondary git worktrees or monorepo subdirectories), IDE MCP hosts spawn stdio servers at fixed user or workspace roots. Without passing explicit `path` arguments on every tool call or implementing stateful MCP `roots/list` notifications, an MCP server risks indexing and checking drift against the wrong worktree.

== 4. Final Decision & Retrospective (`status: discarded`)

1. **Outcome (`decision.outcome: discarded`):**
   * Do **not** re-introduce an MCP server (`CNT-EIDOS-MCP` / `CMP-CLI-MCP-BRIDGE`) or `.mcp.json` installer targets. The architectural decision in `DLT-2026-016` (100% CLI-First + Progressive Agent Skills) and `DLT-2026-094` (Stateless `Stop` Hook `eidos hook`) is empirically validated and retained.
2. **Why the Hypothesis Was Rejected:**
   * The premise that agents comply `< 30%` of the time without MCP was an artifact of pre-`DLT-2026-076` skill fragmentation (`14` separate skills). Under the consolidated 4-skill architecture (`eidos`, `eidos-spec`, `eidos-plan`, `eidos-ops`), top-level coding sessions already achieve **`100.0%` skill discovery**, **`90.5%` `eidos drift` invocation**, **`100.0%` `drift/validate` gate execution**, and **`87.5%` `eidos context` invocation** on tasks requiring discovery.
   * During Regime 0 (`n = 19`), when the MCP server *was* installed, agents invoked MCP tools **`0.0%` (`0/19`)** of the time.
   * A persistent Python MCP stdio process consumes **`75.89 MB` VmRSS** (`3.8x` over the `< 20 MB` budget) for the duration of the IDE session and fails the `< 50 ms` cold-start budget (`186.42 ms` via Typer, `51.29 ms` via fast-path).
3. **Actionable Takeaway for Skill Ergonomics:**
   * Because the only remaining top-level sessions that skip pre-edit `eidos context` in Regime 2 are prompts where the user explicitly attaches `@[file]` paths (`2/5 = 40.0%`), `eidos/SKILL.md` Step 2 (`eidos context -f <touched_file> --json`) remains the right zero-overhead lever without adding an MCP daemon.
