= Exploration: Git-Native Team Auto-Memory Architecture
:toc: left
:icons: font
:sectnums:

== Core Hypothesis

Introducing a **Git-native, team-scoped auto-memory layer** (`type: agent/memory`, stored as one `.adoc` file per entry under `eidos/memory/` and indexed into the existing `eidos/.cache/index.db` knowledge graph)—surfaced automatically through existing `eidos context` slices and `eidos index search` without adding new lifecycle hooks or LLM calls (`POL-004-ZERO-AI-CALL-DEPENDENCY`)—will close the operational knowledge gap between ephemeral coding sessions and formal living specifications (`CNT-*`, `CMP-*`, `CTR-*`, `CAP-*`, `INV-*`, `DEC-*`, `POL-*`), while remaining:

1. **Cross-Agent & Team-Portable (`POL-001-GIT-SOURCE-OF-TRUTH`)**: Engineering corrections, test/build quirks, active project constraints, and external references learned by one developer's agent (Claude Code, Antigravity, Cursor, Codex, Copilot, Cline, Aider, Kilo Code, OpenCode) are committed in Git and immediately available to every teammate and coding harness after `git pull`.
2. **Token-Efficient & Graph-Anchored**: Rather than injecting a static, globally truncated `MEMORY.md` file on every session start, anchoring memories to Eidos entity IDs (`CNT-*`, `CMP-*`, `DOM-*`, `CAP-*`) and file path globs allows `CMP-TIERED-CONTEXT-COMPRESSOR` (`eidos context`) to attach only relevant memories via a separate budgeted pass that never displaces governing architectural entities.
3. **Deterministically Staleness-Aware & Strictly Non-Blocking**: Stamping each memory with `verified_at`, optional `verified_commit`, and optional `expires_at` lets Eidos deterministically compute freshness (`fresh`, `stale`, `expired`, or `unverifiable`) via Git and AST signals in a dedicated `memory_audit` channel—surfaced in `eidos memory audit`, `eidos index health`, `eidos context`, and `CLT-WEB-PORTAL`—without ever triggering blocking `eidos validate`, `--fail-on-warnings`, or `eidos drift` failures when code evolves.
4. **Graduated Governance Pipeline**: Repeated operational lessons captured as lightweight `MEM-*` notes can be promoted into formal `DEC-*`, `INV-*`, or `POL-*` living specifications (`status: promoted`, `promoted_to: <SPEC-ID>`, with optional `DEC-*.graduated_from: MEM-*`), turning ad-hoc session feedback into durable architecture over time.

== Committed Design Decisions

The following product and architectural constraints are locked as inputs to this exploration:

* **Shared Repository Knowledge Only (`eidos/memory/`)**: Eidos owns shared **team** memory inside Git (`POL-001-GIT-SOURCE-OF-TRUTH`). Personal developer preferences (response style, seniority, local IDE habits) are intentionally excluded (no `user` category) so Eidos never collides with client-native personal memory such as Claude Code's private `~/.claude/projects/<repo>/memory/`.
* **Schema Type, One-File-Per-Memory Layout & Collision-Resistant IDs**:
  ** Canonical document type: `agent/memory` (`assets/schemas/v1/agent/memory.schema.yaml` and `memory.template.adoc`), expanding Eidos's canonical schema catalog from 16 to 17 schemas.
  ** One AsciiDoc + YAML frontmatter file per memory under `eidos/memory/mem-*.adoc`, with retired and promoted entries moved to `eidos/memory/archive/` (matching `eidos/deltas/archive/` and `eidos/explorations/archive/`).
  ** Collision-resistant IDs (`MEM-<SLUG>-<4HEX>`, word-boundary trimmed, with on-disk suffix re-roll matching `eidos delta create`) instead of sequential integers so concurrent teammate branches do not collide on merge.
* **Automatic Capture with Explicit Disclosure**: Agent skills instruct coding agents to save high-signal team memories **automatically** via `eidos memory add` and explicitly note the created or updated `MEM-*` file in their response so developers can review, edit, or revert it in Git/PR diffs.
* **Non-Blocking Validation, Dedicated Audit Channel & Drift Isolation**:
  ** Structural YAML frontmatter schema violations in `eidos/memory/*.adoc` are validated by `CMP-SPEC-VALIDATOR`, and `eidos memory add` normalizes/validates generated AsciiDoc bodies to preserve `INV-ASCIIDOC-ZERO-WARNING-HYGIENE`.
  ** Broken or renamed `targets` (deleted files, removed entity IDs), target commit drift, and expired `expires_at` timestamps are routed exclusively through a dedicated **`memory_audit` / `memory_warnings` channel**—never into `ValidationReport.warnings`—so repositories running `eidos validate --fail-on-warnings` or `eidos drift --fail-on-warnings` (`INV-VALIDATION-WARNINGS-PORTAL-AND-CI-ESCALATION`) never fail CI when a memory ages out.
  ** `ChangedFilesClassification` (`src/eidos/vcs/diff.py`) isolates `eidos/memory/**` into its own `memory_files` bucket (separate from `spec_files` and `delta_files`), ensuring memory edits neither mask structural code drift in `CMP-DRIFT-DETECTOR` nor inadvertently break `CMP-HOOK-RUNNER`'s zero-edit Q&A short-circuit (`INV-AGENT-DRIFT-HOOK`) for existing `--hooks` users.
* **Zero New Lifecycle Hooks in Phase 1**: Adding new hook behavior (`SessionStart` memory injection or `Stop` staleness nudges) in `CMP-HOOK-RUNNER` / `CMP-HOOK-MANAGER` / `assets/plugin_reference/hooks.json` is deferred. Discovery relies on `eidos context`, `eidos index search`, and `eidos memory` CLI commands driven by Eidos skills.
* **Living Web Portal Visibility**: Team memories, computed freshness badges, target cross-links, and staleness/promotion health signals must be visible in `CLT-WEB-PORTAL` (`CNT-EIDOS-PORTAL`).

== Findings & Learnings

_Status: `adopted` — All 4 spikes executed against isolated prototypes and live read-only Eidos artifacts (zero mutations to `src/eidos/`); Phase 1 graduated to `DLT-2026-169-ADD-AGENT-MEMORY-SCHEMA-D36A`._

Empirical execution across all four spikes established five decisive architectural findings:

1. **Three Live Leakage Points Must Be Isolated Before Shipping (`Spike 1`)**:
   * Running the current engine on a temporary repository containing `eidos/memory/mem-test-a1b2.adoc` empirically confirmed that (a) `classify_changed_files()` (`src/eidos/vcs/diff.py`) routes `eidos/memory/*.adoc` into `spec_files`, (b) `SpecValidator._check_dict_references()` emits a **blocking** `broken_references` error whenever `targets.paths` contains a deleted `.adoc` path, and (c) `handle_stop_hook()` **blocks a zero-code-edit Q&A turn (`decision: "block"`)** for existing `--hooks` users because `cls.spec_files` is non-empty.
   * All three are cleanly prevented by adding `ChangedFilesClassification.memory_files`, exempting `agent/memory` `targets`/`promoted_to` in `_check_dict_references()` and `_warn_if_deprecated_dependency()`, routing staleness strictly to a dedicated `memory_audit` channel (never `ValidationReport.warnings`), and rejecting `eidos spec create memory` with a redirect to `eidos memory add` (mirroring `create_spec`'s existing `delta/mutation` guard in `src/eidos/core/lifecycle/scaffolder.py`).
2. **`HEAD`-Keyed `memory_freshness_cache` Delivers `326x` Speedup and `8/8` Git Edge-Case Safety (`Spike 2`)**:
   * Live per-memory `git rev-list` checks degrade linearly (`39.9 ms` at `N = 5`, `154.5 ms` at `N = 25`, **`607.9 ms` at `N = 100`**), breaking Eidos's `< 5 ms` context target.
   * Caching freshness in a lightweight `HEAD`-keyed `memory_freshness_cache` table alongside unified `entities`/`edges`/`specs_fts` storage keeps warm anchored + secondary FTS5 retrieval at **`1.36–1.91 ms` median (`4.22 ms` p95 at `N = 100`)** with **`0%` eviction** of primary `TASK_SLICE_ENTITY_TYPES` entities.
   * Checking `git merge-base --is-ancestor <verified_commit> HEAD` resolved **`8/8`** real Git edge cases accurately—gracefully classifying squash-merged/rebased SHAs, `--depth 1` shallow clones, and 0-commit repos as `unverifiable` instead of mass-flagging them `stale`.
   * Secondary memory attachment stayed within `TIER_TOKEN_BUDGETS` across all 3 tiers (`anchor: 210/300 MD`, `guardrails: 776/1000 MD`, `deep: 1741/2500 MD` on `src/eidos/core/index/storage.py`).
3. **Zero-Warning AsciiDoc Sanitization & Calibrated BM25 / Harrier Overlap Thresholds (`Spike 3`)**:
   * Normalizing agent prose (Markdown headings, unclosed code fences, `---` dividers, nested `-`/`*` lists, `include::` directives, and skipped `====` headings) achieved **`0` warnings and `0` errors across `10/10` adversarial fixtures** in `@asciidoctor/core` v3 `MemoryLogger`.
   * Re-embedding the full `149`-item governance corpus on CPU Harrier INT8 exceeded `180 s`, proving `eidos memory add` **must never re-embed specs on the fly**—it must read pre-computed `spec_embeddings` (encoding only `1` candidate query at **`343.1 ms` median**) when `is_semantic_index_complete(conn)` is `True`, and fall back instantaneously (`< 2 ms`) to FTS5 BM25 otherwise.
   * On `20` labeled candidates, duplicate memory detection reached **`F1 = 1.000`** (`6/6 TP, 0 FP`) on both Harrier (`tau_dup_sem = 0.56`) and FTS5 BM25 (`tau_dup_bm25 = 13.5`); spec-overlap detection reached **`F1 = 0.9091`** (`Precision = 1.000`, `Recall = 0.8333`) on Harrier (`tau_spec_sem = 0.59`) vs. **`F1 = 0.8000`** on BM25 (`tau_spec_bm25 = 26.0`).
   * Promotion target lookup resolved **`4/4`** cases (`POL-*`, embedded `INV-*`, embedded `DEC-*` with owning container, and negative rejection).
4. **Dedicated 5th `eidos-memory` Skill Is Mandatory Under `INV-PLUGIN-SKILL-SIZE-CEILING` (`Spike 4`)**:
   * Live measurement showed `assets/plugin_reference/skills/eidos/SKILL.md` sits at **`2,049 / 2,050` words (`1` word of headroom!)**, so inlining the `271`-word memory protocol overflows by `+270` words.
   * Shipping **`eidos-memory` as a 5th bundled skill** (`271` words, proposed ceiling `450`), adding a concise `26`-word trigger to `agents-md/block.md` (`196 -> 222 / 250` template; `201 -> 227 / 320` rendered across all 9 harnesses), and tightening ~15 existing words in `eidos/SKILL.md` to host a 1-line companion pointer satisfies **every existing ceiling with zero regressions**.
   * In a `10`-scenario LLM compliance trial on the draft `eidos-memory` skill, the agent achieved **`10/10` (`100%` precision, `100%` recall)** on save-vs-skip decisions, `100%` disclosure compliance, and revealed one helpful wording refinement: keep recurring toolchain/environment quirks (`pnpm` vs. `npm`) under `feedback` (no TTL) and reserve `project --expires` strictly for time-bounded operational context.
5. **Minimal Portal Payload Overhead & Clean Empty-State Ergonomics (`Spike 4`)**:
   * Adding top-level `memories[]` and `memory_audit` keys to `get_portal_data()` (`base: 3,152.7 KB`, `bundle.html.gz: 1,309.9 KB`) adds just **`+131 bytes` (`0.004%`) at `N = 0`**, **`+2.77 KB` (`0.088%`) at `N = 5`**, and **`+53.35 KB` (`1.692%`) at `N = 100`** while keeping `validation.warnings` completely untouched (`0` warnings) and resolving all 4 target entity classes (`CNT-*`, `CMP-*`, `DOM-*`, `CAP-*`) for inline cross-links.

== Proposed Architecture Blueprint

=== Boundary Between Living Specifications and Team Memory

[cols="2,1,3,2", options="header"]

= Memory: Never mock SQLite in index integration tests
:toc: left

== Guidance
Always construct a real temporary SQLite database via pytest's `tmp_path` fixture when testing `CMP-GRAPH-STORAGE` or FTS5 queries.

== Why
A mocked cursor masked a delete-trigger desynchronization bug in FTS5 shadow tables that only surfaced against real SQLite.

=== CLI Surface (`CTR-EIDOS-CLI`)

[cols="2,4", options="header"]
|===
| Command | Deterministic Behavior (Zero LLM Calls)

| `eidos memory add`
| Generates word-boundary-trimmed `MEM-<SLUG>-<4HEX>` (re-rolling suffix on local collision), stamps `verified_at` and optional `verified_commit`, sanitizes AsciiDoc body (`INV-ASCIIDOC-ZERO-WARNING-HYGIENE`), runs calibrated duplicate (`tau_dup_sem = 0.56` / `tau_dup_bm25 = 13.5`) and spec-overlap (`tau_spec_sem = 0.59` / `tau_spec_bm25 = 26.0`) checks using pre-computed `spec_embeddings` or `< 2 ms` BM25 fallback, and syncs the index.

| `eidos memory list`
| Lists memories filterable by `--category`, `--status`, `--freshness` (`fresh`, `stale`, `expired`, `unverifiable`), `--entity`, `--path`, and `--include-archived`.

| `eidos memory search "<query>"`
| Hybrid BM25 + optional Harrier RRF search scoped to `agent/memory` entries (also searchable via `eidos index search`).

| `eidos memory show <MEM-ID>`
| Displays frontmatter, body, resolved target anchors, and live/cached freshness diagnostics.

| `eidos memory verify <MEM-ID>`
| Re-stamps `verified_at` and `verified_commit` to current `HEAD` (and optionally updates `expires_at`) after confirming the memory still holds.

| `eidos memory archive <MEM-ID>`
| Sets `status: archived` and moves the file to `eidos/memory/archive/`.

| `eidos memory promote <MEM-ID> --to <decision\|invariant\|policy> [--spec-id <ID>]`
| Validates standalone (`POL-*`) or embedded child (`DEC-*`, `INV-*`) `--spec-id` against the live index, records `status: promoted` + `promoted_to`, and moves the memory to `eidos/memory/archive/` without implicitly mutating formal specs.

| `eidos memory audit [--json]`
| Computes deterministic hygiene diagnostics in a dedicated `memory_audit` channel (separate from `ValidationReport.warnings`): missing target paths/entities, target commit drift (`>= 5` commits), expired TTLs, unverifiable history, near-duplicate memory pairs, and spec overlaps. Aggregated into `eidos index health`.
|===
