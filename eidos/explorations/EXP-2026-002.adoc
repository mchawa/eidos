= Exploration: Embedded Architectural Knowledge Graph & Hybrid Context Retrieval Index
:toc: left

== 1. Problem Statement & Motivation

Today, Eidos extracts architectural context slices using `get_context_slice` in `src/eidos/core/context.py`. On every invocation, it:
1. Performs an ad-hoc traversal of the `eidos/` directory via `rglob("*.adoc")`.
2. Parses frontmatter and body on the fly for every specification document.
3. Applies naive set-intersection token matching (`_tokenize_text`) over task descriptions and file path strings.
4. Performs on-the-fly invariant test scans across the entire test suite.

While this zero-dependency approach works well for small repositories, it exhibits significant architectural limitations as repositories scale:
* **Linear Latency Growth:** I/O and parsing overhead scale linearly with the number of specifications, containers, and tests.
* **Lexical Fragility:** Plain keyword token overlap fails to match synonymous engineering prompts (e.g., "secure external webhook ingestion" vs. "INGEST-WEBHOOK").
* **Flat Representation:** Multi-hop architectural relationships (Component -> Provided Contract -> Consuming Component -> Capability -> Invariants -> Test Bindings) require repeated manual graph walks.
* **Token Overhead:** Without a structured multi-tiered compression hierarchy, AI agents are either under-informed (missing invariants) or over-burdened with bloated context.

== 2. Hypotheses & Architectural Topology Under Investigation

This exploration investigates an **Embedded Architectural Knowledge Graph & Hybrid Retrieval Index** stored in a deterministic local cache (`.eidos/cache/index.db`) backed by Python's standard library `sqlite3`.

=== 2.1 The 3-Dimensional Index Model

[cols="1,2,2", options="header"]
|===
| Dimension | Storage & Engine | Purpose
| *1. Architectural Graph*
| SQLite relational tables + Recursive CTEs
| Models typed nodes (`CMP`, `CTR`, `CAP`, `DOM`, `POL`, `INV`, `DS`) and edges (`depends_on`, `provides`, `consumes`, `governs`, `asserts`, `tests`). Enables sub-millisecond $k$-hop blast radius calculations.

| *2. Reverse Code & Test Mapping*
| Relational table with index on path & AST symbol
| Maps source files, package paths, and AST symbols (classes, functions, CLI commands) directly to owning components and active `INV-*` rules.

| *3. Hybrid Search Index*
| SQLite `FTS5` virtual table (BM25 ranking) + exact ID prefix match
| Combines exact identifier matching (`INV-001`, `CMP-CLI`) with BM25-ranked full-text search across capability JTBDs, component responsibilities, and policy rules.
|===

=== 2.2 Git-Native Invalidation & Zero-Drift Guarantee

In compliance with `POL-001-GIT-SOURCE-OF-TRUTH`, the index must never become a stale or desynchronized cache:
* **Mtime & SHA-256 Tracking:** The database maintains an `indexed_files` manifest recording relative paths, modification timestamps, and content hashes.
* **Lazy Incremental Refresh:** On any CLI command or MCP tool invocation, Eidos checks file modification timestamps in <5ms. Only modified or newly created files are parsed and updated in SQLite.
* **Deterministic Rebuild:** If `.eidos/cache/index.db` is deleted or corrupted, it is automatically rebuilt from scratch from the living specifications and codebase.

=== 2.3 Tiered Agent Context Slices

To optimize token consumption in agent context windows, the retrieval engine will support hierarchical context output:
* **Tier 1 (Anchor):** Minimal footprint (~150 tokens) containing matched component IDs, runtime, container type, and direct contract signatures.
* **Tier 2 (Guardrails):** Targeted footprint (~500 tokens) detailing active `INV-*` rules, test coverage status, and governing `POL-*` policies.
* **Tier 3 (Deep Spec on Demand):** Full prose requirements, C4 internal module breakdowns, and schema definitions fetched explicitly via entity ID when needed.

== 3. Key Technical Spikes

=== Spike A: `spike-sqlite-graph-fts`
* **Objective:** Design and benchmark the SQLite schema (`entities`, `edges`, `specs_fts`, `file_mappings`) using pure Python `sqlite3`.
* **Verification:** Run recursive CTE queries to traverse from a modified file up through component boundaries, bound contracts, governing capabilities, active invariants, and test bindings. Verify query execution time is <2ms.

=== Spike B: `spike-incremental-hasher`
* **Objective:** Build and benchmark a fast dirty-checking scanner that compares disk state with SQLite file manifests.
* **Verification:** Benchmark against a simulated repository with 500 `.adoc` files and 2,000 source files. Verify clean-state check takes <5ms.

=== Spike C: `spike-tiered-agent-context`
* **Objective:** Compare agent prompt resolution quality and token consumption between current ad-hoc context slicing and tiered indexed slicing.
* **Verification:** Test against 10 representative engineering tasks (e.g., bugfix, contract update, invariant addition) measuring token savings and agent accuracy.

== 4. Success Metrics & Exit Criteria

The exploration will conclude based on the following quantifiable criteria:
1. **Resolution Latency:** Slicing context for any arbitrary file or task prompt completes in <10ms on repositories with 100+ living specifications.
2. **Token Efficiency:** Tier 1 + Tier 2 slices reduce agent prompt token overhead by >=60% compared to loading full raw specification documents.
3. **Zero External Dependencies:** Built entirely with Python's standard library `sqlite3`, maintaining pure zero-runtime overhead.
4. **Zero Drift:** Automated test suite proves that modifying any spec file or test immediately reflects in the next context slice without manual reindexing.

== 6. Final Decision & Graduation

* **Outcome:** `adopted`
* **Graduating SpecDelta:** `DLT-2026-011`

  The hybrid architecture combining SQLite FTS5 for lexical matching with recursive CTEs for relational graph expansion delivers order-of-magnitude improvements in both latency and precision.
