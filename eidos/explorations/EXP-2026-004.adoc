= Exploration: Dedicated Component Manifests vs Inline Container Components (Centralized Hybrid C4 L3 Architecture)
:toc: left
:icons: font

== 1. Context & Motivation

With the implementation of *DLT-2026-014*, Eidos established a clean first-principles distinction across C4 levels:
* **C4 Level 1 (System Context)**: `SYS-*` / `ARCH-*` defining overall system boundaries, external third-party integrations, and actor personas.
* **C4 Level 2 (Containers)**: `CNT-*` (`type: tech/container` in `eidos/architecture/containers/`) representing separately deployable units, services, libraries, CLI applications, SPAs, and daemons.
* **C4 Level 3 (Components)**: `CMP-*` representing in-process modular building blocks and subsystems encapsulated behind interfaces.
* **C4 Level 4 (Code)**: Classes, methods, functions, and source files declared via `source_path` or `package_path`.

In the original baseline implementation, all C4 Level 3 components were declared **inline** inside their owning container's manifest:

[source,yaml]
----
type: tech/container
schema: schemas/v1/tech/container.schema.yaml
id: CNT-EIDOS-CORE
name: "Eidos Core Engine"
container_type: library
runtime: "Python 3.12+"
package_path: "src/eidos/core"

components:
  - id: CMP-CORE-PARSER
    name: SpecParser
    responsibility: "Parses AsciiDoc files with YAML frontmatter."
    source_path: "src/eidos/core/parser.py"
  - id: CMP-CORE-VALIDATOR
    name: SpecValidator
    responsibility: "Validates frontmatter against canonical schemas."
    source_path: "src/eidos/core/validator.py"
----

While this design is compact and keeps the specification catalog clean and manageable, several architectural challenges arise as systems scale:
1. **Unequal Complexity**: In real-world architectures, some internal components are simple 50-line utility modules, while others are massive subsystems with complex state machines, strict concurrency requirements, or dedicated maintainers.
2. **Scattered Invariants**: When components are strictly inline, they cannot easily host dedicated invariant lists (`INV-*`), local quality attributes, or interface method signatures without bloating the parent container manifest.
3. **Purity of Implementation Code**: An initial spike considered co-locating specification `.adoc` files directly inside source code directories (`src/`, `packages/`). Architectural evaluation firmly concluded that **Eidos specifications must never touch or reside within source code directories**. Source directories must remain 100% pure implementation code. All specifications strictly belong within `eidos/`.

To resolve these tensions, this exploration formalizes the **Centralized Hybrid C4 Level 3 Architecture**.

== 2. Core Trade-Off Matrix

[cols="1,2,2", options="header"]
|===
| Dimension | Option A: Strictly Inline | Option B: Centralized Hybrid Mode (Adopted)

| **Token Economy**
| High baseline efficiency. AI agents retrieve one container document containing the full whitebox view (~400–800 tokens).
| Adaptive. Lightweight modules stay inline (~50 tokens each); complex promoted modules load full deep specifications (~500 tokens) only when directly touched.

| **Specification Density**
| High signal-to-noise ratio. Exactly 1 file per deployable unit prevents documentation proliferation.
| Selective depth. Clean baseline with dedicated `.adoc` files created in `eidos/architecture/components/` only when complexity thresholds are crossed.

| **File Placement**
| Stored centrally in `eidos/architecture/containers/<container>.adoc`.
| **Centralized in `eidos/architecture/components/<component>.adoc`**. Placing specifications in `src/` or `packages/` is **strictly rejected**.

| **Codebase Cleanliness**
| 100% clean source code.
| **100% clean source code**. Eidos never touches or places non-code specifications into source code directories.

| **Granular Invariants**
| Invariants bind primarily to Product Capabilities (`CAP-*`), referencing components by ID.
| Supports container-level capability bindings AND component-specific operational invariants (concurrency, memory ceilings, thread safety).

| **Interface Governance**
| Container owns boundary contracts (`CTR-*`). Internal component interfaces are undocumented or implicit in code.
| Strict separation: **Containers define Boundary Contracts (`CTR-*`)**; **Components define In-Process APIs (`interfaces.provides`)**.
|===

== 3. The Centralized Hybrid Architecture Design

=== 3.1 The 80/20 Governance Rule

Centralized Hybrid Mode establishes a clear operational rule:
* **80% of components remain inline**: Simple internal modules, utility classes, and glue code require no standalone files and stay in `CNT-*.adoc`.
* **20% of components are promoted**: Subsystems with extensive state machines, multi-file internal structures, or strict SLAs receive dedicated living specifications in `eidos/architecture/components/<component>.adoc`.

=== 3.2 The Centralization Mandate: Eidos Never Touches Code

Eidos **strictly mandates that all specifications reside under `eidos/`**, explicitly forbidding placement of `.adoc` files inside source code directories (`src/`, `packages/`):

1. **Source Code Purity**:
   Source code trees are meant exclusively for programming language files, unit tests, and build definitions. Polluting source directories with specification files creates tooling frictions (linters, formatters, packaging scanners) and blurs the boundary between architecture and implementation.

2. **Unified Specification Governance**:
   Having all specifications under `eidos/` provides a single root of truth for all architectural artifacts:
   * `eidos/architecture/system-architecture.adoc` (System Context Level 1)
   * `eidos/architecture/containers/*.adoc` (Deployable Containers Level 2)
   * `eidos/architecture/components/*.adoc` (Promoted Dedicated Components Level 3)
   * `eidos/architecture/contracts/*.adoc` (Boundary Protocol Contracts)

3. **Repository Initialization (`eidos init`)**:
   `eidos init` scaffolds both `eidos/architecture/containers/` and `eidos/architecture/components/`, each tracked by `.gitkeep` files, ensuring clean repository structure from day one.

=== 3.3 Strict Division of Interface Ownership: Container vs. Component

One of the most critical architectural principles in Eidos is clarifying **who defines what interface**:

[cols="1,2,2,2", options="header"]
|===
| Entity | Interface Type | Entity Schema & Location | Nature of Boundary

| **Container (`CNT-*`)**
| **Boundary Protocol Contracts**
| `tech/contract` (`CTR-*`) in `eidos/architecture/contracts/`
| **Process / Network / CLI Boundary** +
Exposed externally to other containers, users, or third parties (REST, gRPC, CLI, MCP).

| **Component (`CMP-*`)**
| **In-Process Module APIs**
| `interfaces.provides` in `tech/component` manifest
| **In-Memory / Language Boundary** +
Internal to the container process. Never called across process or network boundaries (function signatures, traits, ABCs).
|===

* **Why Containers own Boundary Contracts (`CTR-*`)**:
  A Container is the unit of deployment and runtime isolation. Outside consumers communicate with the container's exposed contract (e.g. `CTR-EIDOS-CLI` or `CTR-AUTH-REST`), completely unaware of which internal component handles the request.
* **Why Components own In-Process APIs**:
  Components execute within the same address space. Their interfaces are in-memory language protocols (e.g. `parse_spec(path: Path) -> SpecDocument`). Exposing component interfaces across network boundaries would violate information hiding and couple separate deployables.

=== 3.4 Container Manifest Syntax (Polymorphic Inline + Centralized `ref`)

In Centralized Hybrid Mode, the container's `components:` array supports both inline declarations and relative `ref` pointers to centralized component specs:

[source,yaml]
----
type: tech/container
schema: schemas/v1/tech/container.schema.yaml
id: CNT-EIDOS-CORE
name: "Eidos Core Engine"
container_type: library
runtime: "Python 3.12+"
package_path: "src/eidos/core"

contracts:
  provides:
    - "CTR-EIDOS-VALIDATOR" # Boundary Contract owned by Container

components:
  # 1. Standard inline component (lightweight, zero extra files)
  - id: CMP-CORE-PARSER
    name: SpecParser
    responsibility: "Extracts YAML frontmatter and parses AsciiDoc AST blocks."
    source_path: "src/eidos/core/parser.py"

  # 2. Promoted centralized component reference in eidos/architecture/components/
  - id: CMP-CORE-VALIDATOR
    ref: "architecture/components/validator.adoc"
----

=== 3.5 Dedicated Component Manifest Anatomy (`tech/component`)

When a component is promoted to a dedicated specification, it resides centrally in `eidos/architecture/components/<component>.adoc`:

[source,yaml]
----
---
type: tech/component
schema: schemas/v1/tech/component.schema.yaml
id: CMP-CORE-VALIDATOR
name: "Specification & Schema Validator"
container: CNT-EIDOS-CORE
status: active
package_path: "src/eidos/core/validator.py"
domain_binding: DOM-SPEC-ENGINE

responsibility: >
  Validates living specifications against canonical Draft 2020-12 schemas,
  verifies entity ID conventions, and enforces bidirectional relational graph
  integrity across all architectural layers.

# IN-PROCESS INTERFACES (Language-level APIs, NOT boundary contracts)
interfaces:
  provides:
    - signature: "validate_document(doc: SpecDocument) -> list[str]"
      description: "Validates a single parsed document against its schema and ID regex."
    - signature: "validate_directory(dir: Path) -> ValidationReport"
      description: "Scans directory, validates all schemas, and checks relational links."
  consumes:
    - "CMP-CORE-PARSER"
    - "jsonschema"

quality_attributes:
  stateless: true
  reentrant: true
  max_memory_mb: 64
  max_validation_latency_ms: 50.0

invariants:
  - id: INV-SPEC-VALIDATION
    rule: "Every .adoc file with YAML frontmatter must validate against schema."
    test_binding: "tests/test_validator.py::test_all_specs_conform_to_schema"
---

== 4. Context Retrieval & Token Economy

=== 4.1 Tiered Retrieval Mechanics

[cols="1,2,3", options="header"]
|===
| Retrieval Tier | Inline Component Treatment | Centralized Promoted Component Treatment

| **Anchor Tier** (~200 tokens)
| Displays component ID, Name, and Responsibility (1 line).
| Displays component ID, Name, Responsibility, and spec file link (1 line).

| **Guardrails Tier** (~600 tokens)
| Displays ID, Name, Responsibility, and source path.
| Displays ID, Name, Responsibility, in-process method signatures (`interfaces.provides`), and local `INV-*` invariants. Body prose is omitted.

| **Deep Tier** (~1,500 tokens)
| Displays full inline block.
| Loads the complete dedicated `.adoc` file from `eidos/architecture/components/` including internal architecture, state machine descriptions, and concurrency models.

Consider a scenario where an AI agent works on `src/eidos/core/validator.py`:

* **In a "Strictly Centralized Everything" model**:
  The agent loads `container.adoc` + 7 separate component files with no inline option.
  `Estimated Token Cost: ~3,400 tokens`.

  The agent loads `CNT-EIDOS-CORE.adoc` (where 5 simple modules remain inline at ~40 tokens each) and directly slices the dedicated `eidos/architecture/components/validator.adoc` (`~500 tokens`).
  `Estimated Token Cost: ~780 tokens (77% token reduction)`.

== 6. Verification & Referential Invariants

The Eidos validator and graph indexer enforce three strict invariants in Centralized Hybrid Mode:

1. **`INV-COMPONENT-CENTRALIZATION-MANDATE`**:
   Every dedicated `type: tech/component` manifest **MUST** reside centrally in `eidos/architecture/components/`. Placing specification files inside source code directories (`src/`, `packages/`) is strictly rejected by the validator.
2. **`INV-COMPONENT-CONTAINER-AFFINITY`**:
   Every dedicated `CMP-*` specification must declare `container: CNT-*` matching an existing Level 2 container. Orphaned component files are rejected.
3. **`INV-INTERFACE-BOUNDARY-GOVERNANCE`**:
   Boundary Protocol Contracts (`type: tech/contract`, `CTR-*`) must specify `owning_container: CNT-*`. Components cannot own boundary contracts; they only expose in-process interfaces (`interfaces.provides`).
