== 4. Solution Strategy
* **Git as the OS**: All states (PRDs, ADR-free architectures, task graphs, test bindings) reside in Git.
* **SpecDelta Diff Engine**: Evolutionary changes are semantic mutations (`add`, `modify`, `remove`, `patch`) stored flat with gitignored symlink status views.
* **Multi-Design Systems & W3C Tokens**: Product capabilities bridge business JTBD with technical code packages and W3C tokenized multi-brand design systems.
* **Interactive Hierarchical C4 Explorer**: Living Web Portal provides dynamic, clickable drill-down from C4 Level 1 System Context to Level 2 Container Topologies and Level 3 Component Whiteboxes with breadcrumbs and slide-over component inspection.
* **Embedded SQLite Knowledge Graph & FTS5 Retrieval**: High-speed, zero-dependency caching layer (`.eidos/cache/index.db`) indexing all entities, directed dependency edges, and lexical full-text with sub-2ms dirty checking.
* **Recursive CTE Blast-Radius & Impact Analysis**: Architectural blast radius and k-hop neighborhood traversal executed natively in SQLite via Common Table Expressions (CTEs).
* **Tiered Context Compression Model**: Three-tier context extraction (`anchor`, `guardrails`, `deep`) reducing prompt token payloads by 60-80% for AI coding agents.
* **Token-Budgeted Context Slicing**: Slices bounded C4 topologies, active invariants, and governing policies dynamically for AI agent contexts.
* **Polyglot Invariant Verification**: Continuous drift detection validating automated test bindings across Python, TypeScript, Go, Rust, and Java.

|===
| C4 Level | C4 Term | Eidos Specification Entity | Architectural Boundary

The C4 Level 2 Container Diagram explicitly renders the inter-container dependency connections:
* `CNT-EIDOS-CLI` invokes Core Engine commands (`CNT-EIDOS-CORE`), queries the knowledge index (`CNT-EIDOS-INDEX`), validates plugins (`CNT-EIDOS-PLUGIN`), and hosts/builds the Living Portal (`CNT-EIDOS-PORTAL`).
* `CNT-EIDOS-PORTAL` validates and synthesizes living specifications (`CNT-EIDOS-CORE`) and retrieves graph metrics (`CNT-EIDOS-INDEX`).
* `CNT-EIDOS-DOCS` embeds and links the Living Portal (`CTR-EIDOS-PORTAL`).
* `CNT-EIDOS-PLUGIN` resolves schemas and plugin reference assets (`CNT-EIDOS-CORE`).
* `CNT-EIDOS-INDEX` consumes AST models and frontmatter definitions (`CNT-EIDOS-CORE`).

=== 5.3 Level 3 Component Whitebox View & Interface Governance
Internal component building blocks are declared inline within each container manifest. In Centralized Hybrid Mode (see link:../explorations/EXP-2026-004.adoc[EXP-2026-004]), complex promoted components **reside centrally in `eidos/architecture/components/<component>.adoc`** (linked via `ref:` in the parent container manifest) and point to code via `package_path`. Eidos specifications **never touch or reside within source code directories** (`src/`, `packages/`).

Furthermore, interface ownership strictly distinguishes between deployment boundaries and in-memory linkage:
* **Containers (`CNT-*`)** define **Boundary Protocol Contracts (`CTR-*`)**: Cross-process, network, or CLI protocols (CLI args, REST OpenAPI, gRPC).
* **Components (`CMP-*`)** define **In-Process APIs (`interfaces.provides`)**: In-memory language-level function/class signatures internal to the container.
