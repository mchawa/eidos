= SpecDelta: Add Optional Repository Configuration File (`eidos/eidos.yaml`)
:toc: left

== Problem Statement

Eidos currently relies on hardcoded heuristics, constants, and repeated CLI flags for repository-level engine and workflow behavior:

* **Discovery & File Classification**: Excluded directories (`STANDARD_EXCLUDED_DIRS`), polyglot test file heuristics (`is_polyglot_test_file`), and nested sub-project discovery exclusions require `.gitattributes` workarounds or manual filtering.
* **Drift & Validation Policy**: Teams using `develop` / `trunk` branches, gradual brownfield shadow mode (`--warn-only`), strict body-only co-evolution (`--strict`), `--fail-on-warnings`, non-architectural ignore paths (`scripts/dev/**`, `benchmarks/**`), or granular validator check severities must duplicate CLI flags across local invocations, agent hooks, and CI templates.
* **Velocity-Dependent Thresholds & Ergonomics**: Team operational memory drift (`DEFAULT_MEMORY_COMMIT_DRIFT_THRESHOLD = 5`), context tier token budgets (`TIER_TOKEN_BUDGETS`), semantic model variant / air-gapped mirror URLs, archive retention (`keep_recent = 15`), plugin targets / hook behavior / PyPI update checks, and portal serve/build defaults vary per repository but cannot be committed in one canonical configuration file—nor can developers or agents scaffold, inspect effective merged settings, or query valid config keys offline.

At the same time, introducing a configuration file must preserve Eidos's core constitutional boundaries: zero root-directory clutter in host repositories (keeping `eidos.yaml` strictly inside `eidos/` at `eidos/eidos.yaml`, or `<subproject>/eidos/eidos.yaml` for independent monorepo sub-projects), zero-config operation when absent (`eidos init` never creates `eidos/eidos.yaml` by default), zero duplication of architectural/product truth (`POL-GIT-SOURCE-OF-TRUTH`, which stays exclusively in `eidos/*.adoc`), zero credentials or user-local secrets in Git, zero LLM/AI provider configuration (`POL-ZERO-AI-CALL-DEPENDENCY`), and strict preservation of the 17 canonical living specification schemas under `assets/schemas/v1/` (`INV-SPEC-VALIDATION`, `INV-DOCS-SYNCHRONIZATION`).

== Proposed Specification Changes

=== Canonical v1 `eidos/eidos.yaml` Schema, Env Contract & Architectural Boundary (`CNT-EIDOS-CORE`, `CMP-REPO-CONFIG`, `CMP-ASSET-LOCATOR`)

* **Canonical Placement (`<eidos_dir>/eidos.yaml`)**: Configuration resides exclusively inside the active `eidos/` specification directory (`<repo_root>/eidos/eidos.yaml`, `<subproject>/eidos/eidos.yaml`, or `<custom_path>/eidos.yaml` when `--path` is supplied)—never at the outer repository root. Keeping `eidos.yaml` inside `eidos/` eliminates root-folder clutter, eliminates circular `specs_dir` bootstrap discovery, automatically participates in Portal SSE live reload watching, and keeps each monorepo sub-project 100% self-contained inside its own `eidos/` folder.
