= SpecDelta: Boundary-Aware Direct Mode Symbol Anchoring for Exported Package and Contract Symbols
:toc: left

== Problem Statement

In `src/eidos/vcs/structural.py` (`_SpecDiffInspector.is_anchored` and `_spec_coverage_verdict`), when a modified source file adds any top-level function or class that does not start with `_` (in Python) or has `export` (in TS/JS), Direct Mode requires 1-hop neighbor specifications (or unanchored spec diffs) to either modify `_OWNERSHIP_KEYS` (`components`, `source_path`, `owned_path`, `package_path`) or literally mention the file name or new function identifier in added lines.

While this prevents whitespace-only "touch-to-appease" spec edits, treating every non-underscore module helper function as an architectural boundary symbol forces developers and agents to pollute high-level C4 Level 2/3 container and capability specifications with low-level implementation function names.

== Proposed Specification Changes

1. **Boundary vs. Module-Local Public Symbol Classification (`CMP-AST-SYMBOL-INDEXER`)**:
   * Distinguish **boundary exports** (symbols defined or re-exported in package boundary files such as `__init__.py`, `index.ts`, `mod.rs`, `lib.rs`, symbols explicitly listed in `__all__`, or symbols belonging to files bound as a contract `specification_file`) from **module-internal public helpers** (functions in non-entrypoint submodules that lack a leading underscore solely for intra-package imports).

2. **Boundary-Aware Anchoring in `_SpecDiffInspector` (`CMP-DRIFT-DETECTOR`)**:
   * For **new unclaimed source files** or **new boundary exports** covered only via a 1-hop neighbor spec (such as `CAP-*` or `CTR-*`), continue requiring strict file/symbol anchoring (`is_anchored`) or `_OWNERSHIP_KEYS` updates.
   * For **module-internal functions** within an already-mapped `source_path` / `package_path` where the owning container or component spec (`CNT-*` / `CMP-*`) has a **substantive (non-whitespace, non-comment) diff**, accept the substantive owning spec update without forcing the literal helper function name to be pasted into C4 architectural prose.

== Verification Plan

* Add tests in `tests/test_drift.py` verifying that:
  ** Trivial whitespace/comment touches on specs are still rejected (`trivially_covered_files`).
  ** Adding a new unclaimed file or a new package/contract boundary export still requires explicit file/symbol anchoring.
  ** Adding an intra-package helper function accompanied by a substantive responsibility/prose update to the owning `CNT-*`/`CMP-*` spec passes Direct Mode drift checks without requiring the literal helper function identifier in the spec text.
