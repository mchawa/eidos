= SpecDelta: Polyglot Public Visibility Heuristics, Anchored Boundary Symbol Coverage, and Substantive SpecDelta Apply
:toc: left

== Problem Statement

The structural drift engine (`src/eidos/vcs/drift.py`, `src/eidos/vcs/structural.py`), polyglot AST symbol indexer (`src/eidos/core/index/ast_indexer.py`), and SpecDelta mutation executor (`src/eidos/core/lifecycle/delta_engine.py`) have three precision/recall mismatches:

1. **Broken Visibility Heuristics in Polyglot Languages (False Positives)**:
   * `_is_public_symbol` in `src/eidos/core/index/ast_indexer.py` (lines 916-923) defines a "public symbol" strictly as `not name.startswith("_")`.
   * `AstGrepIndexer.extract_symbols` (lines 228-345) extracts all functions and classes across TypeScript/JS, Go, Rust, and Java/Kotlin without inspecting language-native visibility:
     ** In **TypeScript/JS**, non-exported module-private functions (`function helper()`) do not start with `_`.
     ** In **Go**, unexported package-private functions use lowercase initials (`func parseHeader()`), not `_`.
     ** In **Rust**, private items omit `pub` (`fn helper()`), not `_`.
     ** In **Java/Kotlin**, `private`/`internal` methods do not start with `_`.
   * Consequently, adding any private helper function in TS, Go, Rust, or Java triggers `has_structural_changes == True` and flags false-positive `UNSPECIFIED_CODE_CHANGE` drift.
2. **Trivial 1-Hop Neighborhood Bypass on Existing Files (False Negatives)**:
   * In `_spec_coverage_verdict` (`src/eidos/vcs/structural.py`, lines 460-498), symbol anchoring (`inspector.is_anchored`) is only enforced when `addition.is_new_file` is `True` (line 487).
   * When new public boundary symbols are added to an existing file, any 1-line edit to an unrelated specification in the 1-hop graph neighborhood satisfies `covered_by_spec = True`, even if the new symbols are never mentioned.
3. **Self-Contradictory `// {details}` Mutation Fallback**:
   * In `_apply_expect_or_details_to_spec` (`src/eidos/core/lifecycle/delta_engine.py`, lines 1001-1005), when a `modify_*` mutation lacks an `expect:` block, `eidos delta apply` appends `// <details>` (an AsciiDoc line comment) to the end of the target spec.
   * Yet `_normalized_body_lines` in `src/eidos/vcs/structural.py` (lines 207-220) explicitly strips `//` comment lines when checking whether a spec edit is substantive.

== Proposed Specification Changes

1. **Language-Aware Visibility in `CMP-AST-SYMBOL-INDEXER` (`src/eidos/core/index/ast_indexer.py`)**:
   * Evaluate language-native visibility rules before classifying extracted symbols as public boundary symbols:
     ** **TypeScript / JavaScript**: Require `export` modifier on functions, classes, interfaces, and type aliases (or exported declaration wrapper).
     ** **Go**: Require an uppercase initial character (`name[0].isupper()`) for exported package-level functions, types, and methods.
     ** **Rust**: Require `pub` visibility modifier on `fn`, `struct`, `enum`, `trait`, and `type` items.
     ** **Java / Kotlin**: Exclude `private` and `internal` declarations when classifying public symbols.
     ** **Python**: Respect module-level `__all__` when explicitly defined, falling back to `not name.startswith("_")`.
2. **Require Symbol Anchoring on Public API Additions in `CMP-DRIFT-DETECTOR` (`src/eidos/vcs/structural.py`)**:
   * In `_spec_coverage_verdict`, require `inspector.is_anchored(addition)` (or a substantive edit to the direct owning container/component/contract specification) whenever new public boundary symbols are added (`addition.added_symbols`), rather than only when `addition.is_new_file` is `True`.
3. **Remove `// {details}` Comment-Append Fallback in `CMP-DELTA-ENGINE` (`src/eidos/core/lifecycle/delta_engine.py`)**:
   * Remove the `// {details}` fallback in `_apply_expect_or_details_to_spec`; require either a valid `expect:` block or an explicit non-comment AsciiDoc section/frontmatter update.
