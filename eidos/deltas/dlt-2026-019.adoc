= SpecDelta: Living Web Portal Reading-Friendly Design Revamp
:toc: left

== 1. Intent & Strategic Rationale

The Eidos Living Web Portal (`CLT-WEB-PORTAL`, implemented by `CNT-EIDOS-PORTAL`) is the primary human-facing reading and governance interface for living specifications, C4 architecture topologies, domain capabilities, and SpecDeltas.

While the portal possesses comprehensive functional capabilities—including live AsciiDoc rendering, interactive C4 pan/zoom diagrams, SpecDelta Kanban boards, and CMD+K spotlight search—its current presentation is optimized primarily as a high-density administrative dashboard rather than an inviting, ergonomic reading environment for deep technical study.

In practice, architects, engineers, and product leads spend significant time reading long-form specifications: Arc42 architecture rationale, capability JTBD descriptions, policy rules, and multi-step migration plans. When reading this documentation, users encounter several friction points:
* **Eye Strain from Microscopic Typography**: Body prose is rendered in `12px-13px` (`text-xs`), which is suitable for auxiliary tags or badge labels, but tiring for continuous multi-page reading.
* **Lack of Visual Rhythm & Heading Contrast**: Heading tags (`h2`, `h3`, `h4`) are barely larger than body text (`14px` and `13px`), making documents difficult to scan visually.
* **Unconstrained Line Measures on Wide Monitors**: Text either stretches across ultra-wide viewports (>1200px) exceeding 140 characters per line, or is confined inside small modal dialogs (`Sheet`) with vertical scroll clipping.
* **Cognitive Overhead from Raw Metadata**: Opening any specification forces the reader to confront a 240px-tall raw JSON frontmatter dump before reaching the actual written narrative.
* **Absence of Document Navigation**: AsciiDoc files declaring `:toc: left` have their table of contents directives discarded, leaving readers without an in-page outline or anchor links.

The strategic goal of this SpecDelta is to **elevate the Eidos Living Web Portal into a world-class, reading-first documentation platform**—combining the clean typographic rigor of modern technical publications (Stripe Documentation, GitHub Docs, Next.js, and Arc42) with Eidos's native living specification graph.

== 2. Current Readability Bottlenecks (Gap Analysis)

== 3. Architectural Blueprint & UX Specifications

=== 3.1 Typographic Scale & Design Tokens (`DS-CORE`)
Extend `eidos/design/systems/core/tokens.json` to define formal prose reading tokens adhering to W3C DTCG format:
```json
{
  "typography": {
    "prose": {
      "body": { "$value": "16px", "$type": "dimension" },
      "line_height": { "$value": "1.75", "$type": "dimension" },
      "measure": { "$value": "72ch", "$type": "dimension" },
      "h1": { "$value": "30px", "$type": "dimension" },
      "h2": { "$value": "22px", "$type": "dimension" },
      "h3": { "$value": "18px", "$type": "dimension" },
      "h4": { "$value": "15px", "$type": "dimension" },
      "code": { "$value": "13.5px", "$type": "dimension" }
    }
  }
}
```

=== 3.2 Specification Reader Component (`UIC-PORTAL-READER`)
A dedicated component (`src/eidos/portal/frontend/src/components/ui/SpecReader.tsx`) replacing cramped dialogs:
1. **Header Region**:
   - Document breadcrumb path (`eidos / domains / experience-portal / capabilities`).
   - Title (H1) with prominent visual weight and Document ID chip.
   - Status badge (`● Valid`, `Active`, `Proposed`), schema badge, and target container/domain tags.
   - Collapsible "Raw Metadata" accordion (hidden by default to avoid clutter).
2. **Reading Canvas**:
   - Centered `max-w-3xl` reading column with generous horizontal padding.
   - Typographic rhythm: `h2` elements receive clear top spacing (`mt-10 mb-4`), bottom divider or subtle accent dot, and anchor hash links on hover.
3. **Sticky Outline Navigation (TOC)**:
   - On desktop screens (`>= 1280px`), render a sticky right-hand column (`w-64`) listing all H2 and H3 sections.
   - Automatically highlights the current reading section using `IntersectionObserver`.
   - Clicking any TOC entry smoothly scrolls to the target anchor.
4. **Reader Ergonomic Controls**:
   - Font scale toggle: `Compact` (14px), `Comfortable` (16px), `Large` (18px).
   - Canvas width toggle: `Prose (72ch)` vs `Full Stage`.
   - Source switcher: `Rendered Prose` vs `Raw AsciiDoc`.
   - Copy document permalink / section link.

=== 3.3 Enhanced Admonitions & Callouts
Admonition blocks (`[NOTE]`, `[TIP]`, `[IMPORTANT]`, `[WARNING]`, `[CAUTION]`) rendered with high readability:
* Surface container backgrounds using MD3 tonal tinting (`5%` opacity in dark mode, `8%` in light mode).
* Bold, clear uppercase type pill (`NOTE`, `IMPORTANT`) with matching color glyph.
* 15px body copy with `leading-relaxed` for effortless reading of operational warnings.

=== 3.4 Publication-Grade Code Blocks
Code blocks upgraded to developer-documentation quality:
* Monospace typeface (`Geist Mono`, `JetBrains Mono`) at `13.5px`.
* Syntax token coloring with high legibility on dark and light surfaces.
* Header bar indicating syntax (`AsciiDoc`, `YAML`, `Python`, `JSON`, `Bash`).
* Top-right one-click copy button with animated checkmark feedback.

== 4. Invariant Definition (`INV-PORTAL-READING-ERGONOMICS`)

This SpecDelta introduces and enforces invariant `INV-PORTAL-READING-ERGONOMICS`:
* **Body Text Legibility**: All specification prose rendered within the Living Web Portal MUST have a minimum font size of `15px` (`0.9375rem`) and line-height of at least `1.7` (`leading-relaxed`).
* **Reading Measure**: The default reading viewport for specification bodies MUST be bounded to an optimal reading measure not exceeding `75ch` (`max-w-3xl`) to maintain line length comfort.
* **Heading Hierarchy**: Document headings MUST maintain a minimum `1.25x` hierarchical stepping between levels (H1 >= 28px, H2 >= 20px, H3 >= 17px).
* **Table of Contents**: Any multi-section specification document with two or more H2 headings MUST provide an in-page Table of Contents outline.
* **Non-Blocking Metadata**: Raw YAML frontmatter JSON dumps MUST NOT precede the document title or body; metadata must be rendered as compact chips or collapsible inspector elements.
* **Zero Runtime Dependencies**: The compiled portal bundle MUST remain zero-Node.js/npm at runtime (`INV-PORTAL-ZERO-NODE-DEP`).
