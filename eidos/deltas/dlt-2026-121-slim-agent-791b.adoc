= SpecDelta: Canonical AGENTS.md Managed Block, Skill CLI-Parity and Size-Ceiling Guardrails, and In-Place Skill Tightening
:toc: left

== Problem Statement

=== Bundled skills: small, real inefficiencies and no guardrails

Skills load progressively. Only the 4 *descriptions* sit in the agent's context in every session. A `SKILL.md` body loads only when the skill is activated: the master `eidos` skill in most sessions, the others on demand.

[cols="2,1,1", options="header"]
|===
| Skill | Body words | Description chars (always loaded)
| `eidos` (activated in most sessions) | 2,173 | 571
| `eidos-spec` | 2,284 | 543
| `eidos-plan` | 1,783 | 460
| `eidos-ops` | 913 | 465
|===

A typical session therefore pays roughly 3-6k tokens for skills, which is not a context-window problem. `EXP-2026-007` also showed that the current self-contained 4-skill topology reaches Regime 2 compliance: `100%` `SKILL.md` discovery, `90.5%` `eidos drift`, `87.5%` `eidos context`. Restructuring is not justified. The real issues are smaller:

1. **Descriptions are long keyword lists.** At 460-571 characters each (2,039 total), they are the only always-loaded skill text and drive skill routing, yet they enumerate subcommands instead of stating *when to load*.
2. **The master skill restates itself.** `eidos/SKILL.md` §1 "Constitutional Guardrails" (318 words) re-explains material covered in full later:
** guardrail 3 → §3 mode selection;
** guardrail 5 → §2.1 tool matrix and `eidos-spec` scaffolding rules;
** guardrails 7-8 → §5 gate and review.
3. **Low-information tables.** The `eidos-plan` §2.3 `operation` × `target` matrix (150 words) repeats `add, modify, deprecate, remove` on 12 of 14 rows. The §2.1 tool matrix "Why" column carries marketing phrasing.
4. **Duplicated key lists.** `eidos-plan` §2.2 "Critical Schema Rules" lists the allowed `expect:` keys, which §2.4 then lists again in full.
5. **No guardrails.** Nothing prevents skills from growing, or from referencing commands and flags that are later removed.

A scan of all 176 `eidos …` invocations in the current skills against the live Typer app found *zero* stale commands or flags today. The parity test is preventive.

=== Fragmented, unsafe per-harness rule bridges

`CMP-PLUGIN-INSTALLER` writes a different always-on instruction file for each of 4 harnesses, each with its own hand-maintained copy of the guardrails:

[cols="1,2,2", options="header"]
|===
| Target | File written today | Write semantics
| Cursor | `.cursor/rules/eidos.mdc` (`_write_cursor_rules`) | Whole file owned by Eidos; never refreshed unless `force`
| Codex | `.codex/rules.md` (`_write_codex_rules`) | Whole file owned by Eidos; never refreshed unless `force`. Codex instructions come from `AGENTS.md`, so this file is likely never loaded as guidance.
| Aider | `.aider.conventions.md` (`_write_aider_conventions`) plus `.aider.conf.yml` `read:` | Whole file owned by Eidos; never refreshed unless `force`. It is also Aider's *only* skill index (`/read .aider/skills/<skill>/SKILL.md`), because Aider has no native skill discovery.
| Copilot | `.github/copilot-instructions.md` (`_write_copilot_instructions`) | `<!-- EIDOS_COPILOT_START/END -->` block shared with user content
| Antigravity / Cline / OpenCode / Claude | none (skills only) | n/a
|===

Every supported harness loads the cross-tool `AGENTS.md` standard. GitHub Copilot, Cursor, and Codex have been verified by the maintainer (2026-11-04). Antigravity, Cline, and OpenCode load it natively, Aider loads it via `read:`, and Claude Code loads it via a `CLAUDE.md` `@` import.

Yet Eidos never writes `AGENTS.md`. `docs/guides/agent-plugin.md` already claims that the Cline and OpenCode targets install "AGENTS.md conventions", which is untrue today. The one shared-file writer Eidos has is also unsafe. These defects disappear with the code that this delta deletes:

* **Upgrade bug**: `_write_copilot_instructions` returns early whenever the start marker exists and `force` is false, so `eidos plugin update` never refreshes stale Eidos instructions. Existing Copilot installs are therefore likely carrying outdated guidance today.
* **Data-loss bug**: `_remove_copilot_instructions` keeps only the text *before* the start marker when the end marker is missing, deleting every user line after it.
* **Multiple-block bug**: both functions use `str.split(marker)[0]/[1]`, which silently mishandles duplicated markers.

Users also commonly keep their own `AGENTS.md` (build commands, conventions, team notes). Eidos must coexist with it, not own it.

== Proposed Specification Changes

=== In-place skill tightening

*Rules*:

* Edit the 4 existing `SKILL.md` files only.
* No content is moved to other files, no `references/` directories are added, and every YAML template, example, and CLI command stays.
* Compliance-critical *instructions* keep their meaning, even where wording is compressed: the 8 constitutional guardrails, the Discovery-First tool matrix, Direct vs. Planned criteria, Direct-mode co-evolution rules, the pre-completion gate, and the adversarial review checklist.

[cols="2,3,1", options="header"]
|===
| Location | Edit | Est. saving
| All 4 descriptions | Rewrite as *when to load* triggers, at most 400 characters each (drafts below). | ~900 chars, always loaded
| `eidos` §1 guardrails | Keep all 8 guardrails, but as one-sentence rules with section pointers (e.g. "Select Direct or Planned mode before writing code (§3)"). Detail stays in §2-§5. | ~150 words
| `eidos` §2.1 tool matrix | Keep every row and command; shorten the "Why" column to factual 5-10 word reasons. | ~60 words
| `eidos-plan` §2.3 | Replace the 14-row table with a rule: all entity types support `add`, `modify`, `deprecate`, `remove`, except `SYS-*`/`ARCH-*` (`add`, `modify`) and `INV-*` (`add`, `modify`, `remove`). | ~110 words
| `eidos-plan` §2.2/§2.4 | State the allowed `expect:` keys once (§2.4), with §2.2 pointing to it. | ~70 words
|===

The expected net saving is about 400 words (~6%) of skill bodies plus ~45% of always-loaded description text. The gain is modest by design; the larger value is the guardrails below.

*Draft descriptions* (final wording may differ, but each must be at most 400 characters):

* `eidos`: "Core workflow for repositories governed by Eidos living specs (eidos/). Load before editing code, tests, or specs, refactoring, adding features, or reviewing changes. Covers discovery with eidos context/index, choosing Direct vs. Planned mode, and the eidos drift/validate completion gate. Never create ADRs."
* `eidos-spec`: "Author and edit Eidos living specs: domains, capabilities, personas, C4 containers, components and contracts, decisions, design systems, policies, and INV-* test bindings. Load when creating or changing any .adoc file under eidos/ or binding invariants to tests."
* `eidos-plan`: "Planned-mode workflows: technical explorations (EXP-*), the SpecDelta lifecycle (DLT-*: create, verify, audit, apply), expect: post-conditions, and architectural reviews. Load for new or removed containers/components, breaking contract changes, cross-domain features, spikes, or PR and delta reviews."
* `eidos-ops`: "Eidos setup and operations: eidos init for new repositories, extracting living specs from existing (brownfield) codebases, index and optional semantic search setup, and serving or building the Living Web Portal. Load when onboarding a repository to Eidos or maintaining the index or portal."

=== Skill guardrails

* *`INV-PLUGIN-SKILL-SIZE-CEILING`*: per-skill no-growth word ceilings, set to the post-tightening size (rounded up to the next 50) and never above today's size. It also caps description length, the AGENTS.md block template, and the rendered block.
* *`INV-PLUGIN-SKILL-CLI-PARITY`*: every `eidos` command path and option in the skills and in the block template must resolve against the live Typer app.

=== Canonical `AGENTS.md` managed block

Eidos owns only the text between its named markers. Everything outside them belongs to the user:

[source,markdown]
----
# Acme Billing Service
Run `pnpm test` before committing.          <- user-owned

<!-- eidos:begin agents-md sha256:3f9a1c0b7e2d targets=aider:.aider/skills,claude:.claude/skills · managed by `eidos plugin`; edits inside this block are overwritten -->
## Eidos Living Specifications
- Architecture lives in `eidos/` living specs. Never write ADRs.
- Before structural edits: `eidos context -f <file> --json`.
- Before finishing: `eidos drift --uncommitted --json`.
- Skills (load on demand): `eidos`, `eidos-spec`, `eidos-plan`, `eidos-ops`
  in `.aider/skills/<skill>/SKILL.md`, `.claude/skills/<skill>/SKILL.md`.
<!-- eidos:end agents-md -->

## Team notes                                 <- user-owned
----

*Marker grammar*: `<!-- eidos:begin <name> sha256:<12-hex> targets=<target>:<skills-dir>[,...] ... -->` and `<!-- eidos:end <name> -->`.

* Blocks are *named*, so several kinds can coexist (for example, per-container blocks in the future).
* `sha256` covers the block's inner content after LF normalization, so `git autocrlf` conversions are never mistaken for user edits.
* `targets=` accumulates `<target>:<skills-dir>` pairs for every install that has projected the block, so installing a second target adds its skill location without losing the first.
** Skills dirs are repository-relative POSIX paths, and no manifest discovery is needed.
** Custom `--dest` installs inside the repository participate as `custom:<dest>/skills`. Installs outside the repository, or with a path containing whitespace or commas, skip the block and say so in the install message.
* Entries are sorted by target name before rendering and hashing, so install order never changes the bytes. For example, `aider` then `claude` yields the same block as `claude` then `aider`.
* There is deliberately *no version* in the marker, so Eidos upgrades that do not change content leave user repositories untouched.
* `{{skill_locations}}` renders the skill directories from `targets=`. This preserves Aider's skill index after `.aider.conventions.md` is retired.
* Opt-out is per block, via `<!-- eidos:<name> off -->` anywhere in the file: `<!-- eidos:agents-md off -->` in `AGENTS.md`, or `<!-- eidos:claude-import off -->` in `CLAUDE.md`.
* HTML comments are hidden in rendered Markdown but visible to agents.

*`upsert_managed_block` semantics (install and update)*:

[cols="2,3", options="header"]
|===
| File state | Behavior
| File missing | Create it containing only the block.
| File exists, no block | Append the block (one blank line separator). The user may move it anywhere afterwards.
| Exactly one well-formed block, same rendered content and same targets | No write; return `unchanged`.
| Exactly one well-formed block, content or targets changed | Replace the marker line and inner content in place, wherever the block sits. Bytes outside the markers are unchanged.
| Inner content hash ≠ marker hash (user edited inside) | Do not write; return `modified`. Overwrite only when the user runs an explicit `eidos plugin install --force`. `eidos plugin update` (`update_plugin`, which calls `install_plugin(force=True)`) passes `force=False` to `upsert_managed_block`.
| Opt-out marker `<!-- eidos:<name> off -->` present | Do not write; return `opted_out`.
| Malformed (begin without end, end before begin, duplicate begin for the same name) | Do not write; return `malformed` with line numbers.
|===

*Always*:

* preserve the existing line endings (LF/CRLF) and UTF-8 BOM;
* refuse symlinks via `_check_not_symlink`;
* write atomically (temp file plus `os.replace`).

*Backward compatibility and uninstall: intentionally none.*

* No migration is performed. Bridge files and blocks written by earlier Eidos versions (`.cursor/rules/eidos.mdc`, `.codex/rules.md`, `.aider.conventions.md`, `EIDOS_COPILOT_START/END` blocks in `.github/copilot-instructions.md`) are left in place. Users may delete them by hand, and the docs guide states this.
* `uninstall` keeps its current manifest- and skills-based behavior. It gains no new logic and loses only the calls into deleted functions. It does not touch the root `AGENTS.md` block, the `CLAUDE.md` import block, or the `AGENTS.md` entry in `.aider.conf.yml`, all of which may be left over.
* The one hard requirement is that a fresh install works correctly and never damages user content. This is why shared files are excluded from the manifest `files` list. Plugin-dir manifests already skip paths outside their directory, but `--dest .` would otherwise record a root `AGENTS.md`, and manifest-based uninstall must never unlink it.

=== Decision: `DEC-PLUGIN-SKILLS-SELF-CONTAINED`

* *Decision*: Keep the 4 bundled skills self-contained, with each `SKILL.md` carrying its full instructions, templates, and examples. Optimize only through in-place tightening, and enforce no-growth ceilings and CLI parity in tests.
* *Rationale*:
** Only descriptions are always loaded, so body size is a minor per-session cost.
** The self-contained 4-skill topology is what `EXP-2026-007` linked to Regime 2 compliance.
** Splitting content out would trade a small token saving for a new pull-based failure mode.
* *Rejected alternatives*:
  ** *Progressive disclosure via `references/*.md`*: rejected. Agents would have to *decide* to open another file (the same pull-based weakness behind the `eidos context` gap), skipped templates would raise schema-error rates, some harnesses (e.g. Aider) need an explicit `/read` per file, and no measured problem justifies the risk. It can be revisited only with data from an exploration.
  ** *Split into more micro-skills*: rejected because Regime 1 (14 skills) measured `26.2%` pre-edit `eidos context` compliance.
  ** *Single mega-skill*: rejected because it increases the activated payload for every task.
  ** *MCP tool descriptions instead of skills*: already discarded in `EXP-2026-007` (0/19 adoption, 75.89 MB RSS).

=== Decision: `DEC-PLUGIN-AGENTS-MD-MANAGED-BLOCK`

* *Decision*:
** Project the always-on Eidos bridge as a single named, hash-stamped, target-owned, marker-delimited block in root `AGENTS.md`, written through one shared helper.
** Bridge Claude Code via a `@AGENTS.md` import block.
** Retire all 4 per-harness rule files.
* *Rationale*:
** `AGENTS.md` is the one instruction channel shared by every supported harness, so it replaces 4 divergent copies with 1.
** Marker blocks let Eidos coexist with user-authored content.
** The hash stamp makes user edits detectable instead of silently clobbered.
** The targets recorded in the marker let several installed harnesses share one block, each with its own skill location.
* *Rejected alternatives*:
  ** *Eidos owns the whole `AGENTS.md`*: rejected because users keep their own build commands and conventions there.
  ** *Separate `AGENTS.eidos.md` included from `AGENTS.md`*: rejected because `AGENTS.md` has no cross-harness include syntax, so most harnesses would never load it.
  ** *Keep per-harness rule files*: rejected because of 4 hand-maintained copies, refresh bugs, and no coverage for Antigravity, Cline, or OpenCode.
  ** *Version stamp in the marker*: rejected because it would rewrite every user repository on every Eidos release even when content is unchanged.
  ** *Migrate and clean up legacy bridges, and remove blocks on uninstall*: rejected as unnecessary complexity. Backward compatibility is not a goal, and leftover files are acceptable; correctness of fresh installs is the only requirement.
  ** *Opt-out via new CLI flag or config file*: rejected for this delta because it would change `CTR-EIDOS-CLI` and add a config surface. An in-file opt-out marker is native to the file the user already controls.

== Implementation Plan

Implement as two commits under this delta, so the skill edits and the AGENTS.md projection can be reviewed and bisected independently: (A) in-place skill tightening, ceilings, and parity; (B) the managed block, bridge retirement, and docs. Fresh-install correctness is the only compatibility requirement.
