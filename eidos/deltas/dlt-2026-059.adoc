= SpecDelta: Validate Component source_path, UI Component test_bindings, and Invariant test_binding File & Symbol References in SpecValidator
:toc: left

== Problem Statement

`eidos validate` (`CMP-SPEC-VALIDATOR` in `src/eidos/core/spec/validator.py`) validates that living specifications are authored accurately and that their declared references resolve cleanly. Today, `SpecValidator._validate_source_and_contract_paths` (lines 847-903) only checks `package_path` on `tech/container` and `specification_file` on `tech/contract` when a source tree exists on disk, leaving three categories of disk bindings unvalidated:

1. **Unvalidated `source_path` on `CMP-*` Components (`tech/component` and inline `tech/container` `components[]`)**:
   * Standalone `tech/component` specs (`eidos/architecture/components/*.adoc`) and inline `components[]` entries in `tech/container` specs declare `source_path` (`str` or `list[str]`), but `_validate_source_and_contract_paths` never verifies that those paths exist on disk.
2. **Unvalidated `test_bindings` on `UIC-*` UI Components (`design/ui-component`)**:
   * `design/ui-component` specs declare `test_bindings` (`storybook`, `visual_regression`, `unit_test`, optionally with `::func` selectors), which are never checked for file existence when `status == "active"`.
3. **Unvalidated `invariants[].test_binding` File & Symbol References (`INV-*`)**:
   * `SpecValidator` performs no reference validation on `invariants[].test_binding` (`file::test_func` or `file::Class::test_method`) beyond a basic JSON Schema regex check (`pattern: "^[^\\s]+$"` in `assets/schemas/v1/common/defs.yaml`). `eidos validate` should verify that `test_binding` file and symbol (`::func` / `::Class::method`) references exist on disk—while leaving invariant `INV-*` token matching and coverage enforcement to `eidos drift` and `eidos index sync`.

== Proposed Specification Changes

1. **`CMP-SPEC-VALIDATOR` (`src/eidos/core/spec/validator.py`)**:
   * Expand `has_source_tree` detection in `_validate_source_and_contract_paths` to also consider `(repo_root / "tests").exists()`, `(repo_root / "test").exists()`, or any resolvable `source_path` / `test_binding` file path.
   * Verify `source_path` (`str` or `list[str]`) on active `tech/component` documents and inline `components[]` entries of active `tech/container` documents.
   * Verify `test_bindings.{storybook,visual_regression,unit_test}` (stripping any `::func` suffix before checking file existence) on active `design/ui-component` documents.
   * Collect invariants from active documents (`status` not in `{"planned", "proposed", "draft", "deprecated", "sunset", "rejected"}` across `product/capability`, `product/policy`, `tech/container`, `tech/component`, and `status == "applied"` `delta/mutation`) and parse `test_binding` (ignoring placeholders `N/A`, `TBD`, `NONE`) via `split("::", 1)` into `(file_part, func_part)`:
     ** **File Existence**: Resolve `file_part` via `self._resolve_source_path(repo_root, root_dir, file_part)`. If missing on disk, append a broken reference to `report.broken_references`.
     ** **Symbol Existence**: When `resolved_file` is a single file on disk and `func_part` is specified, verify via `ASTCodeIndexer.list_test_functions` (or polyglot symbol lookup) that the target test function/method exists in `resolved_file`.
     ** **No `INV-*` Token Match in `eidos validate`**: `SpecValidator` will **not** inspect the test body/docstring for `\b<inv_id>\b` token matches (that remains the responsibility of `eidos drift` and `eidos index sync`).
2. **`CAP-PROD-001` (`eidos/domains/spec-engine/capabilities/living-spec-engine.adoc`)**:
   * Update `INV-SPEC-GRAPH-INTEGRITY` rule description to include `source_path`, `test_bindings`, and `test_binding` file and symbol reference integrity.
