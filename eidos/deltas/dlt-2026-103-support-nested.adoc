= SpecDelta: Support Nested Dot-Path Key Resolution in SpecDelta expect.frontmatter
:toc: left

== Problem Statement
In `src/eidos/core/lifecycle/delta_engine.py`, `_evaluate_declarative_postcondition` currently resolves `expect.frontmatter` keys via a shallow 1-level lookup (`actual = target_dict.get(k)`). Consequently:

1. **Nested dictionaries cannot be queried by dot-path**: Assertions on `contracts.provides` (`CNT-*`), `technical.containers` (`CAP-*`), `intent.motivation` (`DLT-*`), or `tokens.manifest` (`DS-*`) fail because `target_dict.get("contracts.provides")` returns `None`.
2. **Arrays of structured objects cannot be queried by field dot-path**: Asserting that a specific `DEC-*` decision or inline `CMP-*` component exists in `decisions:` or `components:` (e.g., `decisions.id: "DEC-VCS-STATIC-INVARIANT-TRACEABILITY"`) fails unless the entire multi-line dictionary is duplicated verbatim.

== Proposed Specification & Engine Changes
1. **Dot-Path Key Resolution (`_resolve_frontmatter_path`)**:
   * When a key `k` in `expect.frontmatter` is not an exact top-level key in `target_dict` and contains `.`, resolve it segment-by-segment:
     - When the current value is a `dict`, advance to `current[segment]`.
     - When the current value is a `list` of dicts (such as `decisions`, `components`, or `invariants`), project `segment` across matching dict elements (flattening nested lists if `segment` itself points to a list field), allowing flat dot-paths like `decisions.id: "DEC-..."` or `components.id: "CMP-..."`.
2. **Leaf-Key Prose Substring Matching (`_PROSE_EXPECT_FIELDS`)**:
   * Check the leaf segment (`k.rsplit(".", 1)[-1]`) against `_PROSE_EXPECT_FIELDS` (adding `"decision"` and `"rationale"`) so dot-paths targeting prose fields (e.g., `intent.motivation`, `decisions.rationale`, `components.responsibility`) support substring matching just like top-level `responsibility` and `rule` fields.
