= SpecDelta: Require Modification Evidence in SpecDelta Verification
:toc: left

== Problem Statement

SHA-256 baselines and `expect:` post-conditions already exist in `verify_delta_mutations`, but four paths still report fulfilment without evidence:

. **mtime fallback**: baselines live in the gitignored `eidos/.cache/index.db` and are recorded by `eidos delta create`. On a fresh clone, or for a hand-authored delta, verification falls back to `target.mtime > delta.mtime`. Observed: the original draft of DLT-2026-038 reported `CNT-EIDOS-CORE` and `CNT-EIDOS-CLI` as `MODIFIED` before any implementation work, because `core.adoc` / `cli.adoc` had been saved after the delta file.
. **Container-granular hashing**: inline `CMP-*` targets are hashed by their whole container file in both `_snapshot_delta_baselines` and `verify_delta_mutations`, so any edit to `core.adoc` (e.g. by DLT-2026-035 or DLT-2026-036) satisfies every component mutation in it.
. **Existence-only structural sub-target checks**: in `_evaluate_declarative_postcondition`, the three structural membership checks (`target_capability` + `target_invariant_id`, `target_container` + `target_component`, and `target_container`/`target_component` + `target_contract`) return `True` as soon as the sub-target is listed on its parent when no `expect:` block is present, and are bypassed altogether when `expect:` is present.
. **Target precedence**: `_extract_mutation_target` iterates a fixed key tuple where `target_capability` precedes `target_component`, `target_contract`, `target_policy`, `target_screen`, `target_ui_component`, `target_invariant_id`, and `target_design_system` (and omits `target_container`, `target_architecture`, `target_client`, and `target_flow`), so `patch_invariant` (or `add_invariant`) mutations that set both `target_capability` and `target_invariant_id` resolve to the capability ID and report `MISSING` forever. DLT-2026-035 is affected today.

== Behavioral Mutations

Implemented in `src/eidos/core/lifecycle/delta_engine.py` (extracted by DLT-2026-038):

. **Action-aware target resolution**: `_extract_mutation_target` prefers the key matching the action suffix (`*_invariant` -> `target_invariant_id`, `*_component` -> `target_component`, `*_container` -> `target_container`, `*_architecture` -> `target_architecture`, `*_contract` -> `target_contract`, `*_policy` -> `target_policy`, `*_screen` -> `target_screen`, `*_ui_component` -> `target_ui_component`, `*_design_system` -> `target_design_system`, `*_client` -> `target_client`, `*_flow` -> `target_flow`) before falling back to the full target key list (including `target_container`, `target_architecture`, `target_client`, `target_flow`) and `details` regex matching.
. **Remove `st_mtime_ns` fallback**: in `_check_or_record_baseline_sha`, if a `(delta_id, target_key)` row exists in `delta_baselines`, return `current_sha != baseline_sha256`; if no baseline row exists yet, record `(delta_id, target_key, current_sha)` in `delta_baselines` and return `False` (`UNMODIFIED`). The `st_mtime_ns` timestamp comparison is removed completely.
. **Symmetric component-entry digests**: inline `CMP-*` targets are digested from their own canonicalized component dict entry (`json.dumps(comp_dict, sort_keys=True, default=str)`, matching invariants) in both `_snapshot_delta_baselines` and `verify_delta_mutations`. Promoted standalone `tech/component` specs continue to use their own file digest.
. **Structural sub-targets as preconditions & post-application `expect:` enforcement**: all three structural sub-target membership checks (`target_capability` + `target_invariant_id`, `target_container` + `target_component`, and `owner_cnt` + `target_contract`) run as preconditions before `expect:` or baseline digest evaluation (`MISSING` if absent). For `modify_*/extend_*/patch_*`, passing the precondition no longer counts as evidence of modification on its own, and `expect:` post-conditions are evaluated before falling back to `delta_status == "applied"` so regressions on applied deltas are caught (`UNMODIFIED`).
. **Contract stability**: no new status values. `eidos delta verify --json` keeps its output shape, so `CTR-EIDOS-CLI` is unchanged. `CAP-PROD-002` adds `eidos delta verify <delta-id> [--json]` to its declared `technical.contracts.interfaces`.

== Verification Criteria

* `tests/test_delta_engine.py::test_delta_verify_requires_modification_evidence` (INV-DELTA-VERIFY-MODIFICATION-EVIDENCE) covers:
** No prior baseline in `delta_baselines` and target file has a newer `mtime` than the delta file → baseline is recorded and status is `UNMODIFIED` (never `mtime`-based); subsequent edit to the target then reports `MODIFIED`.
** Editing a sibling component in the same container leaves the targeted inline `CMP-*` → `UNMODIFIED`, while editing the targeted `CMP-*` entry itself → `MODIFIED`.
** `patch_invariant` (with `target_capability` + `target_invariant_id`), `modify_component` (with `target_container` + `target_component`), and `modify_contract` (with `target_container` + `target_contract`) report `MISSING` if the sub-target is not registered on the parent, and stay `UNMODIFIED` when registered until `expect:` is satisfied or the entity's own digest changes.
** An already-applied delta (`status: applied`) whose `expect:` post-condition regresses reports `UNMODIFIED` (`is_verified == False`) instead of passing on `status: applied` alone.
* `tests/test_delta_engine.py::test_delta_verify_declarative_expect_and_patch_invariant` and the rest of `tests/test_delta_engine.py` still pass.
* `eidos validate eidos && eidos drift --uncommitted` exits 0.
