= SpecDelta: Revamp Eidos Personas and Core Domains Architecture
:toc: left

== Problem Statement
The initial Eidos specifications defined only two personas (`PER-PRODUCT-LEAD` and `PER-AUTONOMOUS-AGENT`) and three domains (`DOM-PRODUCT-CORE`, `DOM-AGENT-HARNESS`, `DOM-VCS-SYNC`). This baseline suffers from significant architectural drift relative to Eidos's actual implementation:

1. **Missing Core Human Personas**: Systems Architects, Tech Leads, Full-Stack Engineers, and Design Technologists represent the primary daily operators of Eidos, yet have no persona representations in the living catalog.
2. **Domain Overload & Conceptual Drift**:
   - `DOM-PRODUCT-CORE` conflated business requirements authoring with technical spec parsing, AST validation, and invariant enforcement.
   - `DOM-AGENT-HARNESS` was conceived as a Docker sandbox runner, whereas Eidos is an agent-agnostic ecosystem providing Model Context Protocol (MCP) servers, context slicing, and workspace skills.
   - `DOM-VCS-SYNC` prioritized third-party issue tracking over Eidos's foundational Git-as-single-source-of-truth philosophy and local drift detection.
3. **No Domain Home for Design & Experience**: Multi-Design Systems (`DS-*`), W3C DTCG tokens, Client applications (`CLT-*`), interaction flows (`FLOW-*`), and the zero-dependency Web Portal (`CMP-EIDOS-PORTAL`) lacked a dedicated DDD bounded context.

== Proposed Architecture & Specification Changes

=== 1. Persona Matrix (5 Personas)
* **`PER-SOFTWARE-ARCHITECT`**: Focuses on C4 container topologies, contract boundaries (`CTR-*`), system policies (`POL-*`), zero-ADR governance, and invariant test coverage.
* **`PER-SOFTWARE-ENGINEER`**: Focuses on Direct Mode spec-code co-evolution, fast flow-state coding, instant drift detection (`eidos drift`), and targeted context delegation.
* **`PER-DESIGN-ENGINEER`**: Focuses on W3C DTCG token studio, multi-client surface management (`CLT-*`), screen state machines (`SCR-*`), and interaction flows (`FLOW-*`).
* **`PER-PRODUCT-LEAD`**: Focuses on customer JTBD, living capabilities (`CAP-*`), hypothesis explorations (`EXP-*`), and Planned Mode SpecDeltas (`DLT-*`).
* **`PER-AUTONOMOUS-AGENT`**: Focuses on token-efficient MCP context slicing, deterministic invariant verification, and Git PR creation.

=== 2. Four Bounded Context Domains (`DOM-*`)
* **`DOM-SPEC-ENGINE`** (`eidos/domains/spec-engine/`):
  - Living specification parsing, schema validation, entity graph resolution.
  - Invariant-test traceability (`POL-002`).
  - SpecDelta mutation lifecycle (`DLT-*`).
  - Owns `CAP-PROD-001`, `CAP-PROD-002`, `CAP-PROD-003`.
* **`DOM-EXPERIENCE-PORTAL`** (`eidos/domains/experience-portal/`):
  - Multi-Design Systems (`DS-*`), W3C DTCG design tokens, and UI components (`UIC-*`).
  - Client applications (`CLT-*`), Screen state machines (`SCR-*`), and Flows (`FLOW-*`).
  - Embedded Living Web Portal daemon (`eidos serve`) and static site generator (`eidos build-site`).
  - Owns `CAP-EXP-001` and `CAP-EXP-002`.
* **`DOM-AGENT-INTELLIGENCE`** (`eidos/domains/agent-intelligence/`):
  - Model Context Protocol (MCP) server integration (`CMP-EIDOS-MCP`, `CTR-EIDOS-MCP`).
  - Targeted, blast-radius-aware architectural context slicing (`eidos context`).
  - Agent plugins, skills, system prompts, and rules.
  - Owns `CAP-AGENT-001`.
* **`DOM-VCS-LIFECYCLE`** (`eidos/domains/vcs-lifecycle/`):
  - Git-native co-evolution (Direct Mode) and Git diff reconciliation (`eidos reconcile`).
  - Real-time spec-to-code drift detection (`eidos drift`) and CI/CD PR gates.
  - Remote VCS bridges (GitHub Actions / GitLab CI, PR status checks).
  - Owns `CAP-VCS-001`.

=== 3. Technical Component Realignment
* `CMP-EIDOS-CORE` -> `domain_binding: DOM-SPEC-ENGINE`
* `CMP-EIDOS-CLI` -> `domain_binding: DOM-SPEC-ENGINE`
* `CMP-EIDOS-PORTAL` -> `domain_binding: DOM-EXPERIENCE-PORTAL`
* `CMP-EIDOS-MCP` -> `domain_binding: DOM-AGENT-INTELLIGENCE`
* `CMP-EIDOS-PLUGIN` -> `domain_binding: DOM-AGENT-INTELLIGENCE`
* `CMP-EIDOS-DOCS` -> `domain_binding: DOM-EXPERIENCE-PORTAL`
