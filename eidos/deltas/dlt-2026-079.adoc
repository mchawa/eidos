= SpecDelta: Structured Mutation Post-Condition Assertions (body/frontmatter) and Closed Schema Validation for SpecDeltas
:toc: left

== Problem Statement

In `assets/schemas/v1/delta/delta.schema.yaml` (lines 246–249), `mutations[].expect` is currently specified as:

[source,yaml]
----
expect:
  type: object
  additionalProperties: true
  description: "Optional declarative post-condition assertions..."
----

This open-ended schema definition introduces five distinct architectural deficiencies into Eidos Planned Mode workflows:

1. **Schema Loophole & Typo Tolerance**:
   While 15 out of 16 v1 JSON Schemas strictly enforce `additionalProperties: false`, `expect` allows arbitrary, untyped keys. Misspelled keys (e.g. `contain:`, `responsability:`, `test-binding:`) pass `eidos validate eidos` without warning, but cause `eidos delta verify` to fail at runtime with opaque `UNMODIFIED` errors.

2. **Conflation of Assertion Verbs and Frontmatter Properties**:
   Assertion verbs that inspect specification body text (`contains`) are lumped together with specification frontmatter keys (`responsibility`, `source_path`, `rule`, `test_binding`, `status`, `version`) in a flat dictionary without semantic separation.

3. **Fragile List and Multi-Substring Evaluation**:
   In `delta_engine.py` (`_evaluate_declarative_postcondition`), `contains` is cast directly to `str(exp_v)`, causing array values (`contains: ["foo", "bar"]`) to evaluate against the literal Python list string `['foo', 'bar']`. Furthermore, list-to-list comparisons check strict equality (`actual != exp_v`), failing valid mutations where `expect` declares a subset of required list elements (such as `source_path` items).

4. **Absence of Negative Assertions & Comment Stripping**:
   Refactoring and deprecation mutations cannot assert the removal of deprecated methods, legacy CLI flags, or dead prose because `expect` lacks `not_contains` assertion verbs, and commented-out tokens (`//` or `////` blocks) are not stripped before evaluating body assertions.

5. **Opaque Verification Diagnostics & Pre-Existing Baseline Vacuity**:
   When an `expect` post-condition fails, `_evaluate_declarative_postcondition` returns a bare boolean `False` and `MutationVerificationItem` emits `status: UNMODIFIED` with no diagnostic indicating which expected key failed or what the actual value was. Conversely, if an unapplied mutation's `expect` block asserts a value already present in the pre-delta baseline, `verify_delta_mutations` previously reported `MODIFIED` without checking whether the target specification's digest actually changed from the baseline.

== Proposed Specification Changes

1. **Close `delta.schema.yaml` with Strictly Structured `body` and `frontmatter` Blocks (`DEC-CORE-STRUCTURED-EXPECT-SCHEMA`)**:
   * Replace `type: object, additionalProperties: true` with a strictly closed schema (`additionalProperties: false`) permitting only `body` and `frontmatter` top-level blocks (no legacy flat top-level keys).
   * Introduce a closed `body` assertion object (`additionalProperties: false`):
     ** `contains`: string or array of strings that must appear in the uncommented AsciiDoc specification body text.
     ** `not_contains`: string or array of strings that must NOT appear in the uncommented AsciiDoc specification body text.
   * Introduce a closed, typed `frontmatter` assertion object (`additionalProperties: false`):
     ** `responsibility`: string assertion for component/container responsibilities.
     ** `source_path`: string or array of strings for component source paths.
     ** `rule`: string assertion for policy and invariant rules.
     ** `test_binding`: pattern-validated string (`^(.+::.+|N/A|TBD)$`) for invariant test bindings.
     ** `status`: enum-validated string covering all v1 lifecycle statuses (`draft`, `proposed`, `planned`, `in_review`, `approved`, `applied`, `rejected`, `in_progress`, `adopted`, `discarded`, `active`, `deprecated`, `sunset`, `retired`, `removed`).
     ** `version`: SemVer pattern-validated string for contracts and capabilities.
     ** `category`: string assertion for policy categories.
     ** `custom`: optional key-value dictionary for non-standard frontmatter properties.

2. **Upgrade `DeltaEngine` Evaluation, Baseline Evidence, and CLI Diagnostics (`CMP-DELTA-ENGINE`, `CMP-CLI-DELTA-COMMANDS`)**:
   * Update `_normalize_expect_spec` and `_evaluate_declarative_postcondition` in `src/eidos/core/lifecycle/delta_engine.py` to enforce strictly structured `expect.body` and `expect.frontmatter` blocks (rejecting unknown top-level or nested keys with explicit diagnostics).
   * Strip YAML `#` and AsciiDoc `//` / `////` comments (`_strip_spec_comments`) and evaluate `body.contains` and `body.not_contains` against the extracted AsciiDoc specification body, supporting both scalar strings and string arrays.
   * Implement list-subset matching when both `actual` and `expected` frontmatter values are lists.
   * Enforce baseline digest modification evidence (`_lookup_existing_baseline_sha`, preferring `vcs.base_commit` / Git history via `_resolve_git_baseline_sha` before SQLite `delta_baselines`) alongside `expect` on unapplied `modify_*` / `extend_*` / `patch_*` mutations so pre-existing baseline values cannot vacuously pass verification.
   * Capture specific diagnostic failure reasons on `MutationVerificationItem.failure_reason` and render them in `eidos delta verify` (`src/eidos/cli/delta_commands.py`).
   * Update `execute_delta_mutations` and `_apply_expect_or_details_to_spec` to apply structured `body` and `frontmatter` blocks.

3. **Update `CAP-PROD-002` Capability & Invariant**:
   * Bump `CAP-PROD-002` to `version: "1.5.0"` and strengthen `INV-DELTA-VERIFY-MODIFICATION-EVIDENCE` in `eidos/domains/spec-engine/capabilities/spec-delta-mutations.adoc` to formalize structured `body` and `frontmatter` post-conditions, comment stripping, list-subset verification, baseline digest evidence, and `failure_reason` diagnostic reporting.
