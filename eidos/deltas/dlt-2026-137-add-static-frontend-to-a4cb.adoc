= SpecDelta: Add Static Frontend-to-Backend HTTP Auto-Linking, Executable Architectural Import Boundaries, and Explicit Epistemic Provenance Tags
:toc: left

== Problem Statement

Eidos maintains a deterministic SQLite + AST knowledge graph (`eidos/.cache/index.db`) and a Git-native `eidos drift` verification gate with zero runtime LLM calls (`POL-004`). Comparative architectural analysis surfaced three structural blind spots in the current engine:

1. **Cross-Runtime Frontend-to-Backend HTTP Blind Spot (`CMP-AST-SYMBOL-INDEXER`, `CMP-INCREMENTAL-SYNC-ENGINE`)**:
   * `_derive_ast_import_edges` (`src/eidos/core/index/sync.py`, lines 1245–1567) only derives `consumes_api` (`CMP-* -> CMP-*`) and `depends_on` (`CNT-* -> CNT-*`) edges from same-language `import` statements (`code_symbols.kind = 'import'`), C#/Java/Kotlin namespaces, `.csproj` `<ProjectReference>` links, and authored `CTR-*.contracts` declarations.
   * Web frontends, portals, SPAs, and backend services communicate across language and container boundaries via HTTP calls (`fetch`, `EventSource`, `axios`, `ky`, Angular `HttpClient`, `requests`, `httpx`) targeting server endpoints (FastAPI, Flask, Express, Fastify, Hono, NestJS, Next.js App Router, Go, Rust, Spring, ASP.NET Core) or OpenAPI `CTR-*` contracts. Today, those cross-boundary runtime couplings remain invisible in `eidos index blast-radius`, `eidos context`, and brownfield extraction (`eidos-ops`) unless manually hand-linked.
2. **Passive C4 Tiers & Unenforceable Cross-Container Import Coupling (`CMP-SPEC-VALIDATOR`, `CMP-DRIFT-DETECTOR`)**:
   * `CNT-*.tier` (`presentation`, `service`, `core`, `persistence`, `extensibility`) and `CNT-*.contracts` in `eidos/architecture/` document architectural layering, yet neither `eidos validate` nor `eidos drift` enforces import boundaries. Nothing prevents a `persistence` or `core` module from importing `presentation` code or bypassing declared boundaries in a brownfield codebase without an explicit ratchet baseline.
3. **Flat Untyped Epistemic Certainty on Knowledge Graph Edges & Slices (`CMP-GRAPH-STORAGE`, `CMP-GRAPH-TRAVERSAL-ENGINE`, `CMP-FTS-QUERY-ENGINE`, `CMP-TIERED-CONTEXT-COMPRESSOR`)**:
   * `edges(source_id, target_id, rel_type)` (`SCHEMA_VERSION` `"2.19.0"`, `src/eidos/core/index/storage.py`) stores authored `x-eidos-ref` links, deterministic AST imports, heuristic ownership inferences, and semantic similarity hits without storing **provenance** or **confidence**. === 5. Architectural Decisions (`DEC-INDEX-HTTP-LINKING-AND-PROVENANCE`, `DEC-CORE-DECLARATIVE-IMPORT-BOUNDARIES`, `DEC-VCS-EXECUTABLE-IMPORT-RATCHET`)

* **`DEC-INDEX-HTTP-LINKING-AND-PROVENANCE` (on `CNT-EIDOS-INDEX`)**:
  * *Decision*: Extract polyglot HTTP endpoints and client requests statically via `AstGrepIndexer` (`POL-004`), link unambiguous single-candidate client prefixes and `openapi`/`http_json` `CTR-*` routes over non-test files into `ast_http` edges and `code_couplings` rows during `sync_index`, and store canonical edge `provenance` (`declared_spec` > `ast_import` > `ast_http` > `ast_symbol` > `inferred_ownership`) and `evidence` in `eidos/.cache/index.db` (`SCHEMA_VERSION` `"2.20.0"`), projecting `observed`/`derived`/`inferred` certainty in `query.py` and `context.py`.
  * *Rationale*: Unlocks cross-runtime SPA-to-API dependency visibility, unmasked call-site coupling counts for boundary ratchets, and certainty-weighted blast-radius queries in sub-millisecond local SQLite without calling LLMs, executing user servers, or inventing ambiguous edges.
  * *Rejected Alternatives*:
    ** *Require external LLM prose generation or runtime HTTP tracing to connect frontend and backend containers*: Rejected because runtime tracing breaks offline CI execution and LLM calls violate `POL-004-ZERO-AI-CALL-DEPENDENCY`.
    ** *Emit edges on loose path-suffix collisions across multiple services*: Rejected because false-positive `depends_on` edges corrupt blast-radius and import-boundary checks.
* **`DEC-CORE-DECLARATIVE-IMPORT-BOUNDARIES` (on `CNT-EIDOS-CORE`)**:
  * *Decision*: Express executable import and HTTP dependency rules declaratively inside `ARCH-*.import_boundaries` (`tier_rules`, `enforce_declared_containers`, `ratchet_baseline`) and `CNT-*`/`CMP-*.import_boundary` (`allow`, `deny`) rather than standalone sidecar JSON configs.
  * *Rationale*: Keeps architectural boundary constraints inside the single living specification source of truth in Git (`POL-001`), validated by `x-eidos-ref` JSON Schemas and inspectable in `eidos context`.
  * *Rejected Alternatives*:
    ** *Store a separate `.eidos-layer-ratchet.json` file outside `eidos/`*: Rejected because splitting boundary rules from C4 tier/container specs breaks `POL-001` single-source governance and invites config drift.
* **`DEC-VCS-EXECUTABLE-IMPORT-RATCHET` (on `CNT-EIDOS-VCS`)**:
  * *Decision*: Enforce `import_boundaries` inside `detect_drift` against the synced `--head` snapshot or working tree over `code_couplings` using monotonically shrinking `ratchet_baseline[].max_imports` ceilings (`observed_imports > max_imports` fails closed; `observed_imports < max_imports` emits advisory `ratchet_shrink_candidates`).
  * *Rationale*: Lets brownfield teams adopt strict C4 layering immediately without blocking on legacy coupling while guaranteeing architectural debt can only decrease over time and commit-range checks never leak dirty working-tree edges.
  * *Rejected Alternatives*:
    ** *Hard-fail on all pre-existing legacy violations with no ratchet mechanism*: Rejected because large brownfield repositories cannot migrate legacy imports in one PR and would disable boundary enforcement altogether.
