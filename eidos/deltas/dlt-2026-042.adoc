= SpecDelta: Enforce Strict C4 Container (CNT-*) vs Component (CMP-*) Target Separation Across Schemas and Validator
:toc: left

== Problem Statement

Although `DLT-2026-014` separated C4 Level 2 Containers (`CNT-*`, `tech/container`) from C4 Level 3 Components (`CMP-*`, `tech/component`), several v1 JSON/YAML schemas and `SpecValidator._check_eidos_ref()` (`src/eidos/core/spec/validator.py`) still allow `components` fields to target `tech/container` (`CNT-*`) and `container` fields to target `tech/component` (`CMP-*`):

1. **`capability.schema.yaml` (`technical.components`)**: Declares `target_types: [tech/component, tech/container]` and `prefixes: [CMP-, CNT-]` even though `technical.containers` already exists as a dedicated required field on `technical`.
2. **`delta.schema.yaml` (`mutations`, `affects`, `blast_radius`)**:
   * `mutations[].target_component` uses pattern `^((CMP|CNT|ARCH|CTR|SYS)-[A-Z0-9_-]+|.*\.adoc)$` instead of `^(CMP-[A-Z0-9_-]+|.*\.adoc)$`, while `mutations[].target_container` (`^(CNT-[A-Z0-9_-]+|.*\.adoc)$`) lacks an `x-eidos-ref` block.
   * `affects.components` allows `target_types: [tech/component, tech/container]` and `prefixes: [CMP-, CNT-]` alongside `affects.containers`.
   * `blast_radius.impacted_components` and `blast_radius.impacted_containers` lack `x-eidos-ref` annotations, and historical deltas place `CNT-*` and `CTR-*` IDs inside `impacted_components`.
3. **`container.schema.yaml` (`dependencies.internal_components` vs `internal_containers`)**: `internal_components` allows `^((CMP|CNT)-[A-Z0-9_-]+|.*\.adoc)$` with `target_types: [tech/component, tech/container]` and `prefixes: [CMP-, CNT-]`, and both fields use the ambiguous `entity_label: container/component`.
4. **`domain.schema.yaml` (`technical_mapping`)**: Only defines `technical_mapping.components` (accepting both `CNT-*` and `CMP-*`), with no dedicated `technical_mapping.containers` property.
5. **`client.schema.yaml` (`container`)**: Allows `^((CNT|CMP)-[A-Z0-9_-]+|.*\.adoc)$` with `target_types: [tech/container, tech/component]` and `prefixes: [CNT-, CMP-]` on a field explicitly named `container`.
6. **Permissive Runtime `x-eidos-ref` Checking (`validator.py`)**: `_check_eidos_ref()` only checks `if val not in catalog_ids`. It never verifies that a resolved entity ID starts with the field's declared `x-eidos-ref.prefixes` or matches `x-eidos-ref.target_types`. Consequently, placing an existing `CNT-*` ID inside a `CMP-*`-only field (when `allow_non_id_string: true` is set instead of a regex `pattern`) silently passes validation.

=== 2. Prefix & Target-Type Enforcement in `SpecValidator` (`CMP-SPEC-VALIDATOR` in `src/eidos/core/spec/validator.py`)
* Track inline component IDs (`CMP-*` declared in `tech/container` `components[]`) with synthetic type `"tech/component"` alongside `report.entity_index` in `_validate_cross_references()`.
* In `_check_eidos_ref()`:
  . If `val` is a recognized Eidos entity ID (`is_entity_id(val)`) and `ref_meta["prefixes"]` is non-empty, require `val.upper().startswith(prefixes)`. Otherwise append a `broken_references` diagnostic reporting that `val` in `field_path` has the wrong entity prefix for `entity_label` (expected `prefixes`).
  . If `val` exists in `catalog_ids` and `ref_meta["target_types"]` is non-empty, verify that the resolved entity's type (from `report.entity_index` or `"tech/component"` for inline components) is in `target_types`.

=== 3. First-Class Container Mutation Actions & Historical SpecDelta Normalization (`CMP-DELTA-ENGINE` in `src/eidos/core/lifecycle/delta_engine.py`)
* Support `add_container`, `modify_container`, and `remove_container` (resolving `target_container: CNT-*`) in `_extract_mutation_target()`, `verify_delta_mutations()`, and `execute_delta_mutations()`.
* Keep `add_component`, `modify_component`, and `remove_component` strictly scoped to `target_component: CMP-*` (where `target_container: CNT-*`, if also present on the same mutation, specifies the owning parent container).
* Support `target_architecture` (`ARCH-*`) on `modify_architecture` mutations.
* Migrate existing SpecDelta manifests (`eidos/deltas/dlt-2026-*.adoc`) where `target_component` or `blast_radius.impacted_components` referenced `CNT-*`, `CTR-*`, or `ARCH-*` IDs so every delta conforms to the stricter schema.

* Placing a `CMP-*` ID inside `technical.containers`, `affects.containers`, `blast_radius.impacted_containers`, `dependencies.internal_containers`, `technical_mapping.containers`, `client.container`, or `mutations[].target_container` fails validation (`eidos validate`).
* `tests/test_validator.py` verifies both schema-level regex rejection and `_check_eidos_ref()` prefix/type mismatch detection when a valid `CNT-*` catalog entity is referenced in a `CMP-*`-only field (and vice versa).
* `eidos validate eidos && eidos drift --uncommitted` exits 0 across all living specifications and historical SpecDeltas.
